Only the Mac was tested this time. For 1.4.3, the asset merge, code rewrite, real play and packaging of the single official App all work end to end; this round ended at the user's latest "wrap up, record, commit" request. Unfinished long-session goals and follow-ups are kept as they are; this round does not count as a full 9 hours, and makes no promise of the whole game or a stable 30/60 FPS. ## Memory comparison for repeated frame-interpolation configuration builds

`long-soak-32` actually observed 10,821.65 s (3 h 0 min 21.65 s) and then deliberately switched to targeted investigation of the repeated growth above; the planned 15,300 s was not completed. All 19 periodic screenshots were checked as normal, no new red diagnostics appeared during monitoring, audio underruns went from 9 to 10 and overruns stayed 0. Then a manual in-game save updated `slot_01/progress.sav`, footprint/caption data etc., and the test process was closed normally. That 99bc package again passed strict signature verification after this real play.

Two directions that had no effect were tested first: a local autorelease pool, and reusing one Metal 4 compiler. Over 12 builds, Metal allocation for both pool variants and the shared compiler still reached about 667.8 MiB; weak references confirmed the old interpolator objects were released. These early experiments fixed the input at 1600×896 and only alternated output between 1080p/1440p, so their numbers cannot be directly compared A/B with the table below, which uses different input sizes; they rule out the guess that these two simple changes fix the current build growth. The real output entry point has its own pool for per-frame temporary objects, which is not counted as evidence of fixing the repeated-build growth; the shared-compiler change was not adopted.

Then the production `totk_mfx.m` was used directly, alternating 12 times between the game's two real size pairs: 1600×896→1920×1080 and 2128×1200→2560×1440. The same diagnostic binary only toggled the cache switch:

| Configuration | Metal allocation observed | Scope |
|---|---|---|
| `TOTK_MFX_FI_CACHE=0` | about 223.75 MiB at build 2, 785.67 MiB at build 12 | Rebuilt every round |
| Default configuration reuse | After warm-up, oscillates between about 174.78–224.00 MiB | No per-round increase after reusing the same configuration |

The probe only creates resources and does not encode interpolation; its footprint is far below the game's real usage, so these Metal allocation differences cannot be converted directly into whole-session RAM savings. Samples taken after fully releasing registered resources, ending the outer pool, completing an empty command buffer and waiting 250 ms are also kept. Evidence `long-soak-32/mfx-resize-*.jsonl`, `mfx-resize-construction-validation.json`; the private comparison source is kept in `procedures`.

The real implementation keeps at most 4 interpolators that exactly match input/output size and colour format, never evicts old entries, and falls back to the original build path when full, so existing configurations are not repeatedly replaced/rebuilt. A native probe cycling through 5 configurations confirms capacity never exceeds 4, the first entry is not replaced, and the fifth can still be built. ## 1.4.3 scene render resolution (TOTK_RENDER_RES, ported external contribution)

`TOTK_RENDER_RES=<w>x<h>` from 1.0.0/1.1.2 is ported to 1.4.3: it only changes the scene render size, UI and output resolution unchanged; when unset or `0` no patch is applied and the game's own sizes are used (handheld 1280x720 / docked 1600x900).

1.4.3's code shape differs from 1.0.0: both dimensions go through `s0` conversion, and `w9` is still used after the patch point by `main+0x585e64` (output size), so `x9` cannot be used for adrp; the purely temporary `x3` in this function is used instead.

| Address | Original instruction | Patched |
| --- | --- | --- |
| `main+0x585e48` | `scvtf s0, w11` | `adrp x3, <data page>` |
| `main+0x585e50` | `str s0, [x19, #0xcc4]` | `ldp s0, s1, [x3, #16]` |
| `main+0x585e54` | `scvtf s0, w10` | `str s0, [x19, #0xcc4]` |
| `main+0x585e60` | `str s0, [x19, #0xcc8]` | `str s1, [x19, #0xcc8]` |

All branches that choose the render size merge at `0x585e48` (the branch at `0x585f50` only reloads w11/w10 and jumps back). The values are written at `+16` of the data page shared with the real-time step patch. All four original instructions are checked before writing; on mismatch it calls `runtime_fail("render resolution patch: main does not match 1.4.3")`, so the main module is never left half-patched.

Verification: branch and register liveness analysis (`x3` is never read or written in the whole function; `x9` liveness confirmed), per-instruction comparison of the originals, Unicorn emulation (before patch 1600x900 / output 1920; after patch 960x540 / output still 1920), and a real 1.4.3 `probe` run on this machine (log shows `1.4.3 render resolution patch: scene render size 960x540`, module self-check `{"status":"pass"}`). Example: `TOTK_RENDER_RES=1280x720`. Unset by default on Mac, so the picture is the same as before (project rule: no resolution reduction on Mac; this variable is only for people who want to tune it themselves).

iPhone / iPad and IPA export (added at merge time, same approach as `game_patches.c`): code cannot be modified on the phone, so the patch can only be compiled in during export on the Mac. It is compiled in only if `TOTK_RENDER_RES` is set at export; at run time the phone first checks the compiled-in instructions, then writes the size to the data page: the phone's own `TOTK_RENDER_RES`, or if unset the game's handheld size 1280x720. If the patch was not compiled in at export, the phone uses the game's own sizes as before, and setting the variable will not change code.

1.2.1 needs nothing separate: it goes through `game_patches.c`, `game_version.h` already has these three addresses, and the original instructions are the same as 1.0.0.

Checks at merge time (M4 Mac): `scripts/verify_v143_output.py` gained render-size cases: unset leaves these four sites unchanged; 960x540 changes exactly these four, data page +16 holds 960, 540, and Unicorn running the patched instructions stores 960, 540 into +0xcc4 / +0xcc8 while the output width at +0xcc0 stays 1920; IPA export compiles the patch in only when the variable is set; a value like `960x540x` is an error (loosening just this one parse makes the check fail). A `TOTK_RENDER_RES` left in the shell does not affect other cases. The iOS branch compiles with the iOS SDK (`-Werror`). Two real sessions (save copy, same shrine entrance): with the variable unset the scene render target is 1600x896 (1.4.3's own size); with `1280x720` it is 1280x720, the half-resolution targets follow to 640x360, and the output canvas stays 1920x1080. ## 1.4.3 scene resolution changeable at run time (runtime_render_request, 2026-10-19)

The patch from the previous section is now always applied (on Mac written at load, on iOS always compiled in at export; `TOTK_RENDER_RES=0` on Mac skips it). When nothing is requested the data page holds the game's own sizes (docked 1600x900, handheld 1280x720), so the picture is as before. The settings menu changes it at run time with `int runtime_render_request(w,h)`: 0 on success, -1 if it exceeds the reservation made at launch (takes effect after restart); `runtime_render_reserve(&w,&h)` gives the reservation limit (compared by pixel count). The input-file command `render <w>x<h>` goes through this too.

- Changing only the data page has no effect: the game only re-reads the size when the mode index changes (`main+0x585da0`). Tried: changing only the data page, nn::oe message 30 plus the display-config pending bit (PR #42's approach), and setting the renderer's cached mode index (+0xcd0) to -1; the scene stayed 1600x896 in all cases. Each frame's graphics update takes the mode-change path when the flags at display state +8 contain 0x280 (`main+0x580b28` → `main+0x585bd0`, forced); writing that flag from outside gets overwritten before it is read. So a second trampoline was added: `ldrh w8,[x23,#8]` at `main+0x580920` jumps to free space in the text segment and ORs in data page +48 (x10 is dead here). The first trampoline also stores the renderer (x19) at +24. The output thread latches requests every frame (`runtime_frame_step_update`): writes the size, sets +48 to 0x80, sets the cached index to -1; when the index returns to a normal value the size has been re-read and +48 is cleared (after 600 frames without a re-read it gives up and waits for the game's own next read). The re-read goes through the game's own mode-change path, and scene targets are reallocated at the new size.
- Canvas scaling (Awis13 b899aa841c): the game multiplies the size by canvas width / 1920. Requested sizes are divided by this factor before writing, and rewritten when the canvas changes (key 3); the game's own sizes are written as is.
- Reservation (formula from Awis13 f9808deb1c): scene targets come from DynamicTextureAllocatorMem, sized at launch by HeapDef. A reservation within 1600x900 needs no heap change; larger needs a `romfs-patches-out/<canvas>-scene-<w>x<h>` overlay (`make_output_res_overlay.py <canvas> --scene <w>x<h> --version v143`; build_app.py generates four: 2560x1440 / 1920x1080 canvas × 1920x1080 / 2560x1440 scene), and the application memory pool is enlarged the same way. iOS can enlarge the heap at launch without any other RomFS: the IPA carries the whole romfs-patches-out and `runtime_heap_overlay` picks the directory. iOS uses `os_proc_available_memory()` at launch: ≥10 GB reserves 1920x1080, ≥5 GB 1600x900, otherwise 1280x720. Mac: memory ≥16 GB reserves 2560x1440, otherwise 1920x1080. If the overlay file is missing it falls back to a level that needs no overlay; `TOTK_RENDER_RESERVE=<w>x<h>` sets it explicitly (a missing overlay is an error).
- iOS canvas: in handheld mode the canvas is 1280x720 (WindowCrop 1280x720), drawable unchanged. Scenes above 720p are supersampled.

Measured (M-series Mac 18 GB, save copy, same cave entrance, `render` via `TOTK_INPUT_FILE`, log lines `[render]` / "the game picked again", screenshots):

| Case | Result |
| --- | --- |
| Docked, 1080p canvas (`TOTK_OUTPUT_RES=0`) | 1600x896 → 960x536 → 1920x1080 → 1280x720, each taking effect the next frame; physical memory 3145 → 3242 MB (1080p scene +97 MB); on the 2560x1440 canvas, 1080p → 1440p scene another +167 MB; does not drop back after shrinking (the heap has been used) |
| Docked, 2560x1440 canvas | Default 2128x1200 (the game applied the factor itself); requesting 1920x1080 writes 1440x810, actual 1920x1080; after key 3 back to the 1920 canvas it rewrites 2560x1440, actual 2560x1440 |
| Handheld (same as phone), reserve 1920x1080 | pass dump: scene target 1280x720 → 1920x1080 → 960x536; 2560x1440 rejected; idle memory after launch with reservation 1920x1080 vs 1280x720 is 3001 / 3005 MB (the reservation itself uses no physical memory); 1080p scene +94 MB |
| No overlay, docked 1920x1080 scene | No crash (only stood still for one minute, which does not prove the heap suffices elsewhere; the overlay is kept as margin) |

`scripts/verify_v143_output.py` now checks: patched by default with stored values identical to the original instructions, `=0` leaves it alone, both trampolines, Unicorn runs the second trampoline (flags contain 0x80 when +48=0x80), on the 2560 canvas a 1600x900 request is written as 1200x675, and over-reservation is rejected. It also fixed two things that were already broken (the fixture lacked `runtime_survey_init`, and the 21:9 patch's words were not in the expected set). iOS: the export step and xcodebuild (iOS SDK, unsigned) both pass, and the exported main carries both trampolines; not tested on a phone.

Merge note (2026-10-21, merging upstream PR #86): upstream's `render_res_publish` in the section below is implemented in this repo by the previous section's `render_write` / `render_latch` (same division by the canvas factor, rewritten by the output thread after key 3 changes the canvas); the heap formula is the same on both sides.

When the canvas is wider than 1920 (PR #86, merged 2026-10-20): the game multiplies the scene size again by "output width ÷ 1920", in both directions (measured: on a 2560×1440 canvas, setting 2560×1440 actually renders 3408×1920; on a 3440×1440 canvas, 6160×2576), and when the scene is larger than 1600×900 `DynamicTextureAllocatorMem` is too small, crashing in the allocator (`main+0x1c2d20` / `0x1c2f20`) after a minute or two. Now the data page holds "requested size ÷ canvas factor", rewritten at launch and when key 3 changes the canvas (before notifying the game), so every canvas renders the requested size. The texture heap, Graphics and the application memory pool grow together by the canvas and scene pixel factors, with 1.6× margin on the scene part (that margin was measured before dividing out the canvas factor, so it is now generous, which is safe). The heap-config overlay is `<canvas>-scene-<scene>` (`make_output_res_overlay.py --scene`, 1.4.3 only); `build_app.py` generates 1920×1080 / 2560×1440 canvases paired with 1920×1080 / 2560×1440 scenes; other combinations stop at launch and print the command that generates them. **Visual change**: when the canvas is wider than 1920, the same `TOTK_RENDER_RES` looks softer than before, because previously it was actually supersampled by the canvas factor; set a larger scene size for a sharper picture. Verified at merge: 2560×1440 canvas + 2560×1440 scene ran 3 minutes with key 3 pressed twice midway, no crash, frame time p50 about 9 ms; `verify_v143_output.py` and `verify_v143_timing.py` pass.

## 1.4.3 fixed resolution (TOTK_FIXED_RES)

The game's dynamic resolution controller (`main+0x584300`, called every frame from the renderer update function `main+0x58196c`) predicts the next frame's cost from 24 frame-time samples and switches the scene resolution between 100 % / 90 % / 80 % levels (measured on a 3024×1890 canvas, the scene varied between 3024×1888, 2712×1696 and 2416×1512). The controller returns the current level's scale as a float in the low 32 bits of `x0`, and the caller stores `cc4 * scale / cc0` into renderer `+0xccc`.

All branches leave through the same epilogue, and only one instruction puts the scale into the return value: `main+0x5848a8`, `mov w9, w23`. With `TOTK_FIXED_RES=1` it is replaced by `mov w9, #0x3f800000` (1.0f): the controller still runs and picks levels as usual, but every level is 100 %. The scene size chosen by `TOTK_RENDER_RES` is unchanged; it just no longer shrinks dynamically. The original instruction is checked before writing; on mismatch it calls `runtime_fail("fixed resolution patch: main does not match 1.4.3")`. The embedded code on iPhone / iPad cannot be changed at run time, so this is Mac only.

Verification (M5 Mac, 1.4.3, 3024×1890 canvas, scene at canvas size): unset, the scene quickly dropped to 2712×1696 after entering a cave; set, the scene stayed at 3024×1888 throughout. Verified only in one scene (an underground cave) and at one canvas size.
