# 1.2.1 Mac port and test log (2026-10-19)

1.2.1 is the version most players have. It changes only the main module `main` and `main.npdm`; `sdk`, `subsdk0` and `rtld` are byte-identical to 1.0.0 / 1.1.2, so it follows the 1.1.2 path (the same system services, no separate patch file like 1.4.3 needed). This round tested only the Mac (Apple M4, 16 GB, macOS 26.5.2), always on save copies.

## Identification

- Update package: `UPD/1.2.1.nsp` (355,645,252 bytes). The CNMT `Patch_0100f2c0115b6800.cnmt` title version is 393216; the version field (0x3060) of the NACP in the Control NCA is `1.2.1`.
- ExeFS (SHA-256): `main` e5aa8d48…efcb6, `main.npdm` 7df836b8…35af39; `sdk` 91573d44…, `subsdk0` 9d04c989…, `rtld` 28317605… are the same as 1.1.2. Full hashes are in `games/totk/assets/expected-v1.2.1.json`.
- `build_app.py` picks the version by these hashes, not by file name.

## Code rewriting and verification

- Rewriting: 31,475 rewrite sites in the main module; the rewritten `sdk` and `subsdk0` are byte-identical to 1.1.2.
- `verify_rewrites.py --version v121`: structure check on 54,640 rewrite sites, per-site equivalence on 54,540 (the 100 syscall / timer gates in sdk get the structure check only); 145,616 of 168,149 trials valid, 0 divergences; all 600 deliberately broken controls caught.
- Atomic windows: the test scans the main module for every "`LDXR w17` / op / `STXR` status w18 / `CBZ w18` out of the window" window and checks it against the list. 1.0.0 and 1.1.2 have two each (the two that used to be hard-coded); 1.2.1 has only one (`0x7ff694`): the function at 1.1.2 `0x74cb68` uses a different register allocation in 1.2.1 and no longer uses x18. 128 scenarios pass, and the negative control with a wrong exit is caught.
- The call-window differential test and the on-device call probe (4 threads, 20,000 calls) pass.

## Patch addresses

`games/totk/scripts/map_version_sites.py` (new tool):

- Code addresses: take the instructions around the patch site in 1.1.2, strip PC-relative fields (B / BL, conditional branches, CBZ / TBZ, ADR / ADRP, literal LDR) and the in-page offset after ADRP, and search the 1.2.1 main module; the window grows from ±6 words until only one match remains.
- Data addresses: mapped through the code that accesses them (ADRP + LDR / ADD); GOT and PLT entries of imported functions are found by the JUMP_SLOT symbol name.
- Function entries: if the instructions around the entry have no unique match, look at its callers; after mapping all call sites, every BL must point to the same place.
- Self-check: mapping 1.0.0 to 1.1.2, all 32 addresses match the existing 1.1.2 table in `game_version.h`.
- 1.1.2 → 1.2.1: 32 / 32 found, and every patch site's original instruction word is unchanged (the output-size BL is still `0x94000083`). `forceSetMatrix` is located consistently by 31 of its 49 call sites, and its body is identical to 1.1.2 apart from branch targets, so the actor fields stay 0x218 / 0x2b4 / 0x2c0 (position reads and writes verified on hardware with the survey).
- `verify_fps60_patch.py` and `verify_realtime_patch.py` emulate the present-interval controller and real-time step on the 1.2.1 rewritten image; positive cases and negative controls pass.

## Real play (binary built in the work directory, save copies)

The test binary lives in a folder whose path is the same length as the desktop App's game directory (102 characters), so Metal's shader cache can reuse the libraries the desktop App already compiled without evicting its entries (see lesson 105 in the original project's claude.md).

1. Shrine save (a shrine interior, selda save slot_00): first frame in 3.9 s, in the world at 41 s (about 5,400 draws per frame). `survey pos` reads the player actor; `survey move` moves Link to Z=88 and the position reading follows. Walking, jumping, pause menu (weapons page, system page), map and weapon quick menu work. The three key-3 modes: MetalFX upscaling (1600×900 → 1920×1080), native 2K (2560×1440), off. Manual save written to slot_01. Audio underruns 0, overruns 0. Closing the window exits cleanly.
2. Loading that 1.2.1 save in a new process: loads slot_01. A save made inside a shrine loads at the shrine entrance (the game's own rule; the save records the position at save time).
3. Overworld save (Mipha Court, slot_05): walking, manual save (2026/10/19 01:22); moved Link 375 m up to die from the fall, chose "Retry" on GAME OVER and the reload returned to the spot before the fall.
4. Loading the overworld save in a new process: Link appears exactly at the save position (3808.51, 590.20, -570.94). In the same session, the negative control with overrides off for fall-death retry: still reloads (see the GAME OVER item above).

Each session had only 3 red error lines, all pre-existing: `SetPointSize`, `SetLineWidth`, and one pre-swizzled texture falling back to the CPU. Session 4 translated 800+ new shaders during play (the player cache came from 1.4.3 / 1.0.0, and 1.2.1 has its own variants), none failed; the packaged first-launch seed has 8,286 shaders (0 skipped).

## Packaging (`build_app.py`)

- Command: `python3.14 build_app.py <base XCI> -k <prod.keys> --update <1.2.1.nsp> -o <App>`, reusing results already in the work directory: 10 minutes total. Of that, signing about 5 minutes, macOS's first check of the new App 208 s, and precompiling 8,286 boot shaders in the App's game directory 98 s (a new process spot check hit 64 / 64).
- App: signature verifies; `CFBundleShortVersionString` 1.2.1, `CFBundleVersion` 393217; same-volume clones, so large files take no extra space.
- Running the game binary inside the App directly (save and cache copies): the first launch with a 1.4.3 shader cache imports the 1.2.1 seed (24,858 files) into the cache, a one-time ~31 s; the title pipeline wait is 128 ms; with a warm Metal cache, background prewarming of 17,780 shaders takes only 6.9 s, and the first entry into the world has no wait.
  One session's prewarm took 237 s and the first world entry waited the full 15 s: Metal's shared cache had been pushed cold by another program (another session was testing iOS at the same time); the next session was back to normal.
- Opening the App through the launcher (`open`, save copies on the system disk under `TOTK/tests/`): the launcher first backs up the save as `profile-before-1.2.1`, the game stops at the title, A loads into the world, and closing the window exits cleanly.
- Note: the ad-hoc signature of a rebuilt App differs from the one previously authorised, so the first time the App touches files outside the bundle on an external volume, macOS shows a "wants to access files on a removable volume" prompt. Players' saves and caches are in `~/Library`, so normal play never hits this; it only appears if, like my first run, test saves are put on an external disk.

The game binary in the App, an overworld save copy, teleporting to a town every 60 seconds (Kakariko, Hateno, Rito, Goron, Zora's Domain, Gerudo, Lookout Landing), 5 laps, 35 stops, 35 minutes:

- Every stop landed on the ground, the same spot per town each lap; screenshots look correct. The Rito Village spot is inside a wooden hut; on two laps the camera was blocked by a wall and the screen was one flat surface, but turning the camera showed it was an interior, not a rendering error.

## Shared shader list (morning of 2026-10-19)

- 1.2.1's shader bytes mostly differ from 1.4.3 (the key is a hash of the control section plus code): only 1,043 of the old seed's 8,286 shaders were already in the list, while all 8,290 of 1.4.3's had been there for a while.
- Merging the translation caches of 9 1.2.1 test sessions (`shader_list.py merge`) into the list: these sessions had 8,298 variants not in the list, including the old seed's default variants and about 1,250 translated during play. 14 of them were also added by the iPhone / iPad backfill (`08937a0`), so on main this adds 8,284 (18,548 → 26,832 variants, 16,591 → 23,867 shaders).
- `locate_shaders.py --romfs extracted/v121/romfs --modules rewritten/v121`: no locator lines needed (the packager can find these shaders in BNSH, `.sharcb` and the game binary by itself).
- Pipelines (`S` / `C` / `R` prewarm lines) not merged: these test sessions recorded 11,052 more lines, but the list's prewarm lines only take the curated title and prewarm lists; pipelines from player sessions stay in each save's `pso_user.tsv`.
- The packaged seed follows the new flow: scan the whole RomFS and game binary, default variants for boot shaders, and one per list binding state for shaders in the list.

## Saves written by 1.4.3

In a save opened by 1.4.3, `option.sav` is in 1.4.3's format (header `0x49E946`, 880 bytes). 1.2.1 still reads it: no warning at the title, and the options screen shows the save's settings (voice language, north-locked minimap and other non-defaults). If `progress.sav` was written by 1.4.3 (same header), 1.2.1 cannot read it; to go back to 1.2.1 use a backup such as `profile-before-1.4.3`, or a save from the 1.2.1 era.
