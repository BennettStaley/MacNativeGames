# Mac performance to-do and retest method

This page keeps the important 2026-10-17 conclusions from the original development tree's `native-port/TODO.md` and `docs/testing-methods.md`, separate from this tool's [1.4.3 log](v1.4.3-port.md). The switches, source and binaries of old experiments must be checked against their specific branch; an old pass or an unmerged experiment does not count as acceptance of the current 1.4.3. This plans the Mac only; it does not mean the iPhone has been tested.

## Conclusions from existing experiments worth keeping

Old M4 / macOS 26.5.2, Lookout Landing save copy, a rendering-capacity test with display pacing disabled; not the real on-screen FPS. Each group used the same binary, 8 balanced alternating 30-second windows. The table gives, per condition, the arithmetic mean of the percentiles of 4 windows, not percentiles of the merged frames; weather and time of day still changed naturally.

| Old experiment | Baseline p50 / p95 (ms) | Experiment p50 / p95 (ms) | Conclusion |
|---|---|---|---|
| Reusing draw-preparation results within a submission | 11.839 / 12.624 | 11.904 / 12.661 | No gain found; p50 about 0.55% slower |
| Copy batching | 11.741 / 12.549 | 11.727 / 12.516 | Actual optimised ops/barriers/saved were all 0; performance not covered |
| 500 µs submission budget | 11.690 / 12.517 | 11.636 / 12.497 | A difference of about 0.46% is not enough to enable it |

Five further submission-budget groups changed p50 by about −0.68% to +0.28%, still no reliable gain; the default policy of 60 draws for the first segment / 75 for later ones stays. A smaller budget for every segment lets the GPU start earlier but adds later idle gaps, so an earlier first start alone does not mean GPU waiting is solved.

Old cost counters: in the encoding stage 99.46% of resource-ID lookups take the fast path, about 11 ns; in the preparation stage the fast path is about 90.22% and the slow path about 566 ns. These include metering overhead and count only the local resolution after taking the lock, not lock waits or the whole function, so they cannot be multiplied by call counts to estimate a frame-rate gain.

The old experiment tree did controlled GPU checks of write-after-read, read-after-write, write-after-write and aliasing: a plain Device barrier does not cover aliases from `mach_vm_remap` / several no-copy buffer wrappers, and ResourceAlias visibility was needed. That correctness conclusion should be kept; the concrete path ported to this tool still needs its own review and positive / negative tests, and another tree's pass record cannot stand in for it. Helper coverage of fill also does not mean the game's real fill path is covered.

## Next priorities

1. **1.4.3 cost baseline.** Fix the build, save, camera, internal and output sizes, cache and presentation mode. First measure total CPU work, the critical path, GPU execution / idle, bytes copied and resource-resolution cost separately.
2. **Preparation-stage slow path and invalidation scope.** First prove repeated work and false invalidation; keep uploads, alias switches, uniform snapshots, GPU write-back and completion lifetimes. Having an encoding thread already does not automatically mean adding more threads raises the frame rate.
3. **Real copy load.** Find the real buffer copy / update fallback, confirm the counters are non-zero, then test dependency batching. Keep the existing uniform rename, and do not turn off existing optimisations to manufacture hits; unknown dependencies, overlapping ranges and aliases must be handled conservatively.
4. **Long-term memory.** Separate the game heap, the serial table, texture-pool slots, pipeline / driver caches, the residency set and the objects actually alive after GPU completion. `mtl_dead_forget` currently conservatively keeps destroyed serials; before shrinking the table, slot reference relationships must be completed so the old premature-forget bug does not come back. 1.4.3's frame-generation config reuse only targets repeated builds; other growth still needs attribution.
5. **First-compile stutter.** Record cold and warm caches separately on the same route and collect full frame times. Relative spike logs miss ordinary slow frames; screenshot FPS, fixed-camera averages and generated-frame counts cannot prove a stable 30/60.
6. **Scenes, actions and real displays.** Check complex abilities / combat / cutscenes, menu teleports and cross-scene resource retirement, long stretches of rapid mode switching, physical 4K and high refresh rates separately. Version comparisons must use the same machine and load; do not compare single FPS figures from different games / devices.
7. **Split the DM_NVN_TBDR bundle.** DM_NVN_TBDR=1 made world frames slower on an M3 Pro (frame p50 18.5 → 25.5 ms, GPU p50 15.1 → 16.3 ms) and dropped depth-only passes ("pass without Metal targets: depth serial …"). Each piece now has its own switch, DM_NVN_TBDR_{STORE,UDC,XV,LOAD,DS,HOIST,DEFER,FUSE,ZSKIP,RANGE,GUARDS}=1 (default off); every piece also applies GUARDS (mid-submission commits, async shaders and layered passes off), so measure GUARDS alone first and read each piece against it. A `[tbdr]` log line every 600 frames gives per-piece hits, CPU ms per frame and dropped passes. Prime suspects: GUARDS for the CPU-side frame time (no mid-submission commits serialises encoding and GPU work), DS for the dropped passes.

## Minimum record for each test round

- Record the commit, uncommitted diff, new source files, the actual binary's SHA-256, the selected version / asset hashes and the environment; a commit name alone is not enough.
- Use a separate profile and a unique shared game slot, with user processes taking priority; never run two game / GPU probes in parallel.
- Each performance candidate gets at least 8 × 30 s in A/B/B/A/B/A/A/B order, keeping every slow frame. Keep sampling, reference-resolution checks, screenshots and heavy diagnostics in windows separate from the actual timing.
- Separate world, menus, loading and cutscenes; record real monotonic time, frame number, position / view, weather and cache changes. State the limits of any variable that was not strictly fixed.
- Report p50/p95/p99/max of the full frame distribution and the share over budget; do not average percentiles and present them as a merged result, and do not add overlapping CPU/GPU times.
- Check the real picture and execution errors at the same time. For copy groups record the ops/barriers/saved deltas; a zero count means not covered.
- For memory keep RSS, footprint, process peak, Metal allocation, resident objects and release after completion separately; a single total cannot prove a leak or a plateau. Record the time window of heavy diagnostics.
- Record passed, no gain, not covered, failed negative control and interrupted tests separately; do not drop stutters or anomalies to chase a score.

The old target of p95 ≤ 10 ms in representative scenes is a milestone, not yet a whole-map promise; 1.4.3 must establish its own baseline. Single correctness fixes, version ports and memory improvements should also be reported separately, not all called FPS gains.

## Three conclusions on an M3 Pro (18 GB, 120 Hz ProMotion) (2026-10-20)

Same outdoor save copy (Sky Temple), camera still, background muted window, 1080p output / the game's own scene size; each row is the median of the one-line-per-300-frames log over a 30–40 s window. "Over the beat" is the count newly added to the present-pacing log line: presents whose interval is more than half a refresh longer than the cap intends (at a steady 60 every frame is held for two refreshes, so the "held more than one extra refresh" share is 100%, but over the beat is 0). Once the screen locks, the system no longer reports present times and the GPU behaves differently, so windows during screen lock are not in the tables below.

### Automatic frame cap (`framerate.cap = auto`, Mac default)

| Setting | Frame time p50 / p95 (ms) | Actual frame rate | Held for two refreshes (criterion) | GPU busy |
|---|---|---|---|---|
| 120 (old default) | 10.63 / 12.04 | about 94 | 28.3% (all jitter) | 96% (incl. keepalive) |
| 60 | 16.68 / 17.83 | 60 | over the beat about 0.2% | 94% (incl. keepalive 8.3 ms/frame) |
| Auto | 16.66 / 17.94 | 60 | over the beat 0.2–0.5% | 72–75% (keepalive turned off automatically) |
| Auto, native output (old: about 65 fps, 84% held for two refreshes) | 16.6 / 17.9 | 60 | over the beat 0.8–1.3% | 78% |

- At 1080p this machine cannot sustain 120 (frame time excluding the pacing wait p90 about 11.6 ms); Auto drops to 60 about 2.5 s after entering the game, taking the average frame rate from about 94 to 60 in exchange for every picture staying on screen for the same time. 1440p and native also hold 60.
- At lower tiers the measured frame time is off at both ends: the GPU finishes the previous frame during our pacing wait, so the game's wait for it gets shorter (7.0 ms at 60 fps, 10.6 ms uncapped); with keepalive off the idle GPU clocks down, so at 30 fps a 1080p frame takes 20 ms of GPU and 26 ms overall and looks like it cannot even hold 40, yet it recovers as soon as the tier goes up. So besides "10 calm seconds", a step up is also tried after holding the current tier for 20 s; if the try fails (drops again within 5 s), the p95 at that moment is remembered, the same tier is not retried for 5 minutes (unless p95 drops by more than 10%), and the wait doubles. Frames within 0.5 s after a stall of 100 ms or more (screenshots, disk reads) and within 2 s after an output / scene size change are not counted.
- With frame generation 30+30 / half refresh rate, frame generation paces itself and Auto steps aside; on return it resumes from the last tier. The iOS default is still the display refresh rate (not measured on an iPhone).

### GPU keepalive made adaptive (`TOTK_GPU_KEEPALIVE` unset / `auto`)

On the old M4, keepalive took world-scene GPU time from 12.1 ms to 9.1 ms. On the M3 Pro, alternating in the same scene (6 windows of 240 frames each time, ABBA order on-off-off-on-on-off):

| Frame cap | Keepalive on: frame / GPU (ms) | Keepalive off: frame / GPU (ms) | Spin kernel GPU time | GPU busy (on → off) |
|---|---|---|---|---|
| 120 | 10.61 / 7.06 | 10.57 / 7.00 | 3.45 ms/frame | 96% → 78% |
| 60 | 6.85–7.09 / 6.1–7.3 | 6.86–7.06 / 6.7–10.2 | 8.3–9.3 ms/frame | 94% → 72–75% |

Frame time does not differ (with it off the GPU clocks down and per-frame GPU time at 60 fps is 0.5–3 ms longer, but still within budget), while the spin kernel wastes 3.5–9 ms of GPU per frame. Now it is measured once after entering the game and kept only if frame time is at least 3% faster, remeasured every 30000 frames and after the frame cap changes; `=1` is always on (old behaviour), `=0` off. On the M4 it is expected to still choose "on"; not retested on an M4.

### GPU memory after switching output size

Before: after 1080p → 1440p → native → 1080p → native → 1080p, GPU allocated memory went 3322 → 3961 MB (+640) and footprint 4583 → 5436 MB (+850), and switching back to 1080p did not bring it down. In the residency set breakdown all the growth was on the nvn_mtl.m line that creates game textures (350 at 386 MB → 557 at 1062 MB, almost none removed); in the shared storage table these entries all still had holders, and each was the most recently initialised texture at its address: the game's DynamicTextureAllocator keeps a canvas / scene render target per output size and reuses them on switching back (the second entry into native creates almost nothing new). On hardware they are just bytes in the game's fixed heap; here each is a separate Metal texture. This is not growth of the game heap itself, nor a serial leak.

Now: shared storage entries that were last drawn before the size change, had been a render target for at least 120 frames before that, and have not been a render target for 1200 frames since are released (the holder re-resolves on next use, and texture-pool slot views are dropped too; otherwise the views still hold the base texture, which leaves the residency set without being freed: the first version removed 320 MB from the residency set but GPU allocated memory did not drop). Textures drawn only once and only sampled afterwards (cube maps and the like) never reach 120 frames and are left alone; with no size change nothing is released, so the frozen picture of the pause menu is unaffected. After the same switch sequence: GPU allocated 3312 → 3607 MB (+295), resident 4627 → 4957 MB (+330; two repeats: 3308 → 3604), and about 1200 frames after each switch it prints `render targets not drawn into ... released` (75–310 MB each time). The remaining ~300 MB is still on the same registration line: `TOTK_STOR_DUMP=1` shows about 90 MB of it are targets in the 1440p canvas chain that the game still draws after switching back to 1080p (parts at 1280x720 / 640x360 / 2560x1440), the rest not further attributed; it no longer grows with the number of switches. These memory figures were measured after the screen locked (which does not affect allocation, but there are no present statistics while locked, so frame-pacing numbers only use windows before the lock). `TOTK_RT_EVICT=0` turns it off (A/B).

## Low-risk performance changes (2026-10-21, none A/B tested in game on this machine)

- **Pipeline prediction keeps scanning after it hits its budget (upstream #166, b5cbbca).** When a submission's prediction scan stops at the budget (almost always 8192 commands when entering a new area), the next miss in the same submission continues from there, up to 32 times; 64 keys each time, pending table of 768 entries. Upstream report on 1.2.1 / M4 Max: pipeline time in long frames 35.8 s → 5.5 s. `TOTK_PSO_RESCANS=0` goes back to one scan per submission. Compare the "compiled synchronously on the submit thread: N" count in the per-submission parallel-precompile stats line.
- **Small RomFS reads go through a 256 KiB block cache (tvc97 9be79b5).** On entering the world the game reads thousands of adjacent small files, each a cold pread; now reads under 256 KiB are copied from 256 KiB-aligned blocks of the image (Mac 64 MB / iOS 16 MB, least recently used evicted first), so adjacent files share one disk read. Only the game image itself is cached (by image offset): files replaced / added by mods or this tool's patches go through their own override file's fd, bypassing the cache, and mod files still take priority; mods load only at startup and the image is read-only, so the cache never returns stale data. `TOTK_ROMFS_CACHE=0` turns it off; with `TOTK_ROMFS_MMAP=1` reads go through mmap and also bypass the cache. Logs: `RomFS block cache: N block reads for M small reads`; `TOTK_FS_TIMING=1` prints `[totk-fs] read window … wall_ms=…` every second. `probe-fs` compares 2000 random small reads (including cross-block) against direct reads on 1.4.3, and also passes with a test mod.
- **The refresh rate comes from the display the game window is on.** `mtl_display_hz` used to read the main display (`CGMainDisplayID`): with the window on a 120 Hz secondary display and a 60 Hz main display, the whole session paced at 60 and the Auto frame cap only chose among 60-based tiers. Now frontend.m records the window's display, and a counter increments when the window moves to another display or the display mode changes (refresh rate changed in System Settings, display plugged / unplugged); `mtl_display_hz` caches by that counter, and present pacing (`g_paced_hz`, the uncapped clock limit), the Auto frame cap (re-picks tiers from scratch on a new Hz), the display link's frame-rate range and the present-pacing statistics all follow. No switch (behaviour differs only with multiple displays); `DM_PRESENT_HZ=<hz>` can still force the pacing. Whether the frame rate is "uncapped" is still decided only at startup from the display at that time. Logs: `[totk] window display N (name, H Hz): …`, `[nvn] the window's display changed: A Hz -> B Hz`, `[auto-cap] B Hz display: starts at …`.
- **When the game sets shaders, variants already in the cache are precompiled in the background (upstream #186, 646ce29, ported by hand).** With `TOTK_SHADER_PREFETCH=1` (default off, as upstream), `nvnProgramSetShaders` hands the variants of that program's shaders already in the translation cache to the background (up to 4 compiling at once) to build Metal libraries, passed to the submit thread through `warm_enqueue` / `warm_claim`, so the first draw gets the library directly. No translation, no skipped draws; pipelines are still built at draw time. Upstream 1.1.2 / M5 Max: frames waiting on libraries 102 frames / 278 libraries (44 minutes, longest 4.3 s) → 2 frames / 3 libraries (13 minutes, longest 0.5 s); the cost is about 6000 extra libraries compiled in the background, so it stays off by default. The only conflict with this branch's async shaders (bfdd085) was the declaration in totk_shader_rt.h; `totk_rt_variant` keeps `may_defer`. Log: a `[prefetch]` totals line (programs, shaders queued, compiled, total background ms).
- **Draws inside an occlusion count may be skipped too (upstream 311f7ec).** While their shader is being prepared in the background, draws inside an occlusion query are skipped as well, and a count left at 0 because of that reports 1, so objects are not culled by mistake. `TOTK_OCCL_SKIP=0` goes back to translating on the spot. Log: `[occl] … raised to 1 so far`.
- **Shaders for later draws that cannot be skipped are prepared at once, in parallel (upstream bc461fc).** On the first missing shader the rest of the submission is scanned, and draws that cannot be skipped go to the urgent translator threads (`TOTK_RT_URGENT_WORKERS`, default 4); background translator threads default 2 → 4 (`TOTK_RT_BG_WORKERS`). `TOTK_SHADER_PREDICT=0` turns it off. Merged by hand with this branch's prefetch background counters. Log: `[shader-predict] scan …`.
- **The submit thread no longer writes the shader files of variants translated elsewhere (upstream 7305d4e).** No switch.
- **Prediction scans continue only after a scan that found something; the pipeline scan is limited to 4 ms per frame (upstream f134a7b).** `TOTK_PSO_PREDICT_FRAME_US` (default 4000), `TOTK_SHADER_PREDICT_FRAME_US` (default 0 = unlimited). Check the scan time on the per-submission parallel-precompile stats line.
- **Compute shaders go to the urgent translators too, and a dispatch waits for them instead of being skipped (upstream ebe621d).** No switch; the `[shader-miss]` line saying a compute shader is not translated yet and its dispatch is skipped should no longer appear.
- **The pipeline key ignores blend factors of targets that do not blend and missing colour targets (upstream f3e2f66).** Recorded warm-up lists are normalised the same way when read, so duplicate pipelines are built only once. Pipeline archive keys change with it: affected pipelines compile once more the first time.
- **Pipeline prediction resolves programs and binding variants not drawn yet from shaders already loaded (upstream 6915f64).** `TOTK_PSO_PREDICT_UNSEEN=0` turns it off. Log: `parallel precompile up to submission …: … draws scanned whose program or binding variant was not resolved yet …`.
- **Shader libraries of predicted variants compile in the background, and their draws wait for them (upstream 65b4a1f).** `TOTK_PSO_PREDICT_LIBS=0` turns it off. Log: the "… shader libraries started in the background for predictions, … taken by draws" part of the same stats line.
- **Until a border-colour pipeline is ready the draw uses the plain pipeline, and warm-up builds them from recorded recipes (upstream b06c88d).** Only in effect with async shaders on; `TOTK_BORDER_PLAIN=0` goes back to compiling on the spot. The list gains `B` lines. The README test counts keep this branch's numbers.

## GPU time towards 120 Hz (2026-10-21, none A/B tested in game on this machine)

On the M3 Pro a 1080p frame takes about 10.6 ms; 120 Hz needs 8.3 ms. One switch and one commit per item; to compare, fix 1440p output, frame cap 120 and the Sky Temple save copy, about 2 minutes per group, and look at the frame time p50 / p95 of the one-line-per-300-frames log and the per-pass GPU times in `TOTK_PASS_GPU`'s `[pass-gpu]`.

- **Narrow barriers between render passes (`TOTK_BARRIER_NARROW`, default 1; tvc97 12ca537, ported by hand).** Previously each replay encoder had a full barrier at its start and end, and the GPU drained between passes. Now at the start of a render pass only copies / compute are ordered before all stages and earlier rendering before this pass's fragment stage, so the next pass's vertex stage (binning) can overlap the previous pass's fragments; when this pass first meets a draw whose vertex side (vertex / tessellation / geometry) reads a texture, image or storage buffer, or when an earlier render pass may have written storage / images, it first waits for all earlier vertex and fragment work (`bar_draw`, or `RS_VERTEX_WAIT` through the encoding stream). Render targets are all private textures that share no memory with buffers, so vertex fetch only sees bytes written by copies / compute or storage writes, both of which are already ordered. Copies, compute, MetalFX and helper passes keep full barriers. The copy encoder's ResourceAlias visibility is merged into the closing Device barrier (one barrier, two options). In the old tree removing all barriers (racy) took frame time 11.82 → 10.66 ms, and DavidZande's branch measured 10–13% less GPU time on 1.0.0; the gain from narrow barriers should be below that ceiling. `=0` goes back to full barriers, `=2` skips the vertex dependency check (for measurement only). Log: on the first and every 20000th time, `[barrier] narrow passes: N of M render passes waited …`. `probe-gpu-vertex-wait` (a 10 ms producer pass + a consumer pass whose vertex stage reads it, 12 rounds, Metal validation layer) passes; the negative control does not wait, but the race itself did not reproduce (timing), so correctness rests on reflection, not on the probe catching a race. Risk: wrong pictures (flicker, textures a frame late) rather than crashes; watch the picture during A/B.
- **Waiting for uploads uses a condition variable (`TOTK_UP_WAIT_CV`, default on; upstream #159 a).** `q_cb` (before the submit thread opens a helper command buffer) and `mtl_finish` used to poll `g_up_pending` every 200 µs / 1 ms; now the completion callback decrements the count under `g_up_slot_mu` and broadcasts, and waiters sleep on `g_up_slot_cv`. This saves up to one polling period of latency per QueueFinish / helper command buffer (a bigger gain during loading than in in-game frame time). `=0` goes back to polling. `probe-gpu-upload-batch` passes. No extra memory.

- **QueueFinish does not wait for queued presents (`TOTK_FINISH_PRESENTS=1` restores the old behaviour; upstream #159 b).** `nvnQueueFinish` waits only for submitted GPU work; queued presents hold only a by-value copy of tex_t, so `nvnMemoryPoolFinalize` / `nvnTextureFinalize` first wait until queued presents from that memory range / texture are handed to the GPU (no wait if there are none). Internal calls and probes still use `mtl_finish` with presents, and `mtl_drain` on suspend / exit still flushes all presents. The gain is in loading (one or two beats saved per QueueFinish), not frame time. Compiled only, not tried in game.

- **Uniform copies take only the range the shader reads (`TOTK_CB_EXTENT=1` turns it on, default off; upstream #159 c, nxnative b0a9079).** The inline-update copy (`upd_shadow`) used to copy the whole binding every time; the game often binds a full 64 KiB block and changes only a small part (upstream measured about 80 copies / 3.8 MB per frame on 1.4.3). When a shader loads, its MSL is scanned once (`cb_extent_scan`): if a user uniform binding's name appears only in `<name>)._m0[<integer>]` reads and in the argument struct declaration, and the block is the translator's `float4 _m0[4096]`, the highest index + 1 float4s is recorded; the copy length is that rounded up to 256 bytes, never more than the binding itself. A computed index (even in one place), the block passed whole to a function or taken by reference, a different block layout, an index ≥ 4096, no MSL source, or pass dump on all fall back to copying the whole block. In this Mac's 1.4.3 seed cache, 7,471 of 74,117 cbuf bindings fall back to the whole block, and 64,052 are ≤ 2.5 KB. Logs: when on, one startup line `TOTK_CB_EXTENT=1: uniform copies take only the bytes the shader reads`; to compare, the existing per-interval `[nvn]` uniform copy line reports new copies N / X KB, and X should drop clearly. `probe-gpu-drv-c0` gained 12 extent checks (needs game data; the same function already ran 10 checks here in a standalone program). Memory: copies come from the arena recycled at every submission and only get smaller, so nothing is held longer; each NvShader gains 256 bytes (`cb_ext[64]`, present even with the switch off). When different shaders read different lengths, the same block gets several copies (the key is address + length) and the table (`UBO_SHADOW_MAX`) wraps sooner, but each copy is much smaller. #159's footprint growth should not come from this item (more likely lazy clears or the upload-wait change; not checked). Risk: a missed case in the scan lets a shader read arena bytes beyond the copy, showing as flicker / wrong colours / deformed models, not a crash; compiled only, not tried in game.

- **Lazy clears (`TOTK_LAZY_CLEAR=1`, default off; upstream #159 d, rewritten in `nvn_lazy_clear.h`).** When targets are set with a full-target clear pending and no draw in between, a clear-only render pass used to be opened (cleared, stored, then loaded again by the next pass that attaches it); now the clear is recorded (up to 8 sets), and the next draw that attaches the same texture / level / layer through the same view in a new pass takes it over as loadAction = Clear; a newer clear of the same subresource replaces an older one. Only single-sample 2D, non-block-compressed targets that own their storage are deferred: only this one serial in the shared storage table, not a format view, and no other entry (including handed-off ones) overlapping its memory; with `TOTK_TEX_SHARE=0` nothing is deferred. The clears land (as before, one clear-only pass per set, in recording order): before any replayed operation other than setting targets / clears / state and bindings / uniform updates (copies, texture clears, compute, counters, events); when a uniform update's target overlaps the memory of a waiting target; before any draw that does not take it over (one that samples it by serial or memory overlap, attaches it through another view / level / layer or in an already open pass, or has attachments of different sizes, since loadAction clears only the render area); before a pass is opened by anything other than a draw (scissored / masked clear quads, MetalFX, post-processing, cube group replay); and at the end of each top-level command list and each submission, so presents, QueueFinish and CPU readbacks never see a waiting clear. A clear that was taken over by a draw that was then skipped stays in R and lands, as rp_flush does, before the next operation above. No extra memory (a set is just a p_set_rt copy and the clear values, no textures or buffers); upstream's footprint growth 11.2 → 14.4 GB has nothing to do with this item; the cost is one scan of the shared storage table per deferral. Not in effect with `DM_NVN_TBDR=1`. Logs: one line `TOTK_LAZY_CLEAR=1: …` when on, and on the first and every 20000th takeover `[lazy-clear] taken N, landed M of K deferred clears (pass P)`. Compiled only (`-fsyntax-only` and `nvn_mtl.m.o`), no probe (a probe needs the whole runtime build), not tried in game. Risk: wrong pictures (something not cleared that should be: ghosting, last frame's content, black / garbled blocks, especially in shadows, the G-buffer and the bloom chain) rather than crashes; watch the picture during A/B.

Upstream reports #159 as a whole raising the footprint 11.2 → 14.4 GB; neither c nor d holds memory longer (c only shrinks copies, d only records target lists and clear values), so the growth must come from other changes; not attributed.

- **The residency set is committed only when its members really changed (`TOTK_RES_DEDUP`, default 1; the remaining item of tvc97 3a5d46f, nxnative df7badd).** `g_res_objects` mirrors the residency set one to one; re-adding an object already in the set or removing one not in it used to mark the set for a commit as well, so the next `res_commit` did a whole-set `[g_res commit]`; now both cases return at once without marking. The saving is mostly submit-thread CPU time (the driver reorganising the residency set); the effect on GPU time is indirect. `=0` goes back to the old behaviour. Logs: one startup line `TOTK_RES_DEDUP=1: …`, then every 16384 checks a line `residency: N checks, M commits, K redundant adds/removes skipped`; M/N should be clearly lower than with `=0`. The same commit also brought the crash report gate (`crash_gate.h`: when several threads crash at once only the first prints, and it exits if printing is not done in 15 s; no switch) and totk_xlate patch 0006 (texel offsets read from registers are no longer treated as constants; the prebuilt binary is updated; the 1.4.3 seed is unchanged, and two agl_technique_pfx compute shaders now translate). The rest of 3a5d46f (lazy clears, uniform ranges, QueueFinish, the upload condition variable, the three threads.c items) was already ported by hand on this branch; the automatic frame-cap recovery probe (`nvn_cap_auto.h`, mainly for iOS, not tested on an iPhone) conflicts heavily and has nothing to do with GPU time, so it was not ported. Compiled only, not tried in game.

### #159 c / d measured (2026-10-22, M3 Pro)

Sky Temple save copy, the user's settings (4K output, 1800p scene cap, frame cap 120, GPU saturated), background and muted, auto-loading the save; 130 s per run, taking the median of the one-line-per-300-frames reports after frame 2400, in the order baseline / c / d / d / c / baseline.

| Condition | Frame time p50 / p95 (ms) | GPU p50 / p95 (ms) | New uniform copies per frame | Footprint |
|---|---|---|---|---|
| Baseline (two runs) | 17.98–18.07 / 19.38–19.39 | 14.46–14.61 / 15.00–15.11 | 268 / 3.89 MB | 4645–5096 MiB |
| `TOTK_CB_EXTENT=1` | 18.09–18.29 / 19.39–19.61 | 14.63–14.76 / 15.13–15.25 | 280 / 0.66 MB | 4601–4612 MiB |

## CPU-side ports (2026-10-22, compiled only, not tried in game)

- **Buffer out-parameters no longer go through the autorelease pool (upstream #287).** The `id<MTLBuffer> *` out-parameters of `arena_alloc` / `driver_bank_gpu` / `widen_u8_gpu` are `__autoreleasing` by default under ARC, so each of the several stores per draw cost a retain + autorelease; as `__strong` they are just stored into the caller's local variable. Behaviour unchanged, no switch, no log; in upstream's `sample`, the replay thread's autorelease share went 2.63% → 1.73%.
- **Border-colour variant keys are reused across draws (upstream #286, ported by hand).** Every draw that bound a sampler with a border colour Metal lacks used to build its key in `border_key` with `appendFormat:` (`%a` floats), up to three times per draw, then build a string to look up in a dictionary. Now each shader remembers, per stage, the samplers it last read (argument id, axes, colour, the whole `samp_par`, compared bit for bit) and the key object built from them, and returns the same object when they match; `fs_fn_border` remembers the last key object → function per nodepth, and `vs_fn_for` remembers 4 entries (fs, layered, key object → function), all compared by object address; nil (still compiling in the background) is not remembered. This branch has no upstream `border_filtered` / recipe, so it was rewritten for this branch's key format; the static locks inside the original functions became `g_bpatch_lock` / `g_vpatch_lock`. No switch, no log; upstream `sample`: `pso_get` 11.7% → 3.4%, key building ~5.6% → 0. Risk: a false hit gives wrong edge colours on those textures, not a crash.
- **A write-back waits only for the submission that rendered it (`TOTK_WB_FENCE`, default on; tvc97 0871b71, ported by hand).** `wb_write_list` used to wait for all submitted GPU work with `mtl_finish_gpu()`, so the game thread waited for the frame in flight on every write-back; now `wb_note` records for each rendering the fence of its submission (`g_fence + 1` during replay), and a write-back waits only for the largest fence in the batch, then for uploads to finish (`up_pending_wait`). This branch's `wb_ent` is the snap version (small targets ≤ 256 KiB compare bytes); only a `fence` field was added. `=0` goes back to waiting for everything. Log: every 5 seconds a line `[writeback] last 5.0 s: N calls holding the game's thread X ms in all (… average, … longest)`; for A/B look at X and longest. Risk: a wrong fence reads a texture not finished drawing (flicker, wrong blocks), not a crash.
- **Renderings are written back to memory in batches, one GPU wait per batch (`TOTK_WB_BATCH`, default on; tvc97 811115c, ported).** Pool-invalidation write-backs used to open one command buffer per texture per level and wait for each (the roughly 110 ms stall after spawning in DavidZande's branch on 1.0.0); now all levels and layers of up to 64 textures / 64 MB are copied into one buffer by one command buffer, waited for once, then reswizzled into the pool one by one. Freshness and superseded checks are unchanged (including this branch's snap byte comparison). `=0` does one at a time. Logs: the existing `[writeback] ser=… GPU rendering written back to memory (N textures / M MB so far …)` line as before; for stalls see the `[writeback] last 5.0 s` line from the previous item; new probe `make probe-gpu-wb-batch` (6 shapes, batched and one by one, needs the runtime build, not run this time). Risk: a wrong reswizzle offset misplaces written-back textures (terrain normals, crosshair picking); the probe covers it.
- **ReadTexels / WriteTexels move only the region asked for (`TOTK_TEXELS_REGION`, default on; tvc97 096d023, ported).** Reads and writes of CPU pool textures used to deswizzle / reswizzle the whole layer each time and unprotect the whole range on writes (DavidZande's branch on 1.0.0 measured the game writing small blocks into a 5120x5120 texture 6–29 times per frame, about 2 × 13 MB each); now `nvn_deswizzle_region` / `nvn_swizzle_region` copy only the region, and writes unprotect only the block rows the region covers (`nvn_region_span`). This branch's existing GPU region conversion (`texels_gpu_region`, used when the whole layer is ≥ 1 MiB, one submission and one wait) now comes after the CPU region path: by default the CPU region path takes the request, and only when it declines (unsupported layout) or with `=0` does it fall back to the GPU region / whole-layer path, so `=0` equals the behaviour before the port. No new log; this branch's existing `[texels-gpu] reads=… writes=…` counters should barely grow when it is on. `make probe-texel-region` (27,150 cases against whole-layer copies) and `probe-texture-auto-layout` pass here. Risk: a wrong region offset misplaces small blocks the game writes (map, UI textures) or reads the wrong bytes.
- **The replay thread's per-draw CPU cost (`TOTK_REPLAY_FAST`, default on, `=0` goes back to the old path; 2026-10-22, compiled only, not tried in game).** Why: only one frame is in flight, and the G-buffer pass's roughly 2040 draws take 2.5 ms to replay before it can be submitted, so the GPU idles about 2.2 ms per frame and every microsecond the replay thread saves per draw turns almost 1:1 into frame time. Four changes: (1) `prog_get` became `prog_get_raw`, returning `void *`, so both cache hits no longer go through ARC's `objc_retainAutoreleaseReturnValue` + `objc_unsafeClaimAutoreleasedReturnValue` (about 180 samples / 15 s at the start of `draw_inner`); (2) `uw_ui_squeeze` first checks "6 indices, has a vertex shader, squeeze not off", so most draws no longer do 13 shader-name comparisons (about 115 samples); (3) the recording copy `flatten_recording` first walks the record headers to get the total length and allocates once, instead of growing by repeated `realloc` from 4 KiB and shrinking again (about 330 samples of memmove in `EndRecording` on the game's recording thread); (4) the pool lookup's thread caches are merged into one `_Thread_local` struct, so a lookup takes the thread-local address only once (no switch, pure code generation). Behaviour, ordering, residency and uniform snapshot semantics are all unchanged; for A/B look at the `TOTK_TIMELINE` frame p50 and the replay wall time. Not done: the `tex_by_id` slow path (`tex_mtl` validation + rebuilding the view every time, about 200 samples; a CPU-mirrored texture's dirty-page generation changing revalidates everything, and saving it needs per-page generations), the residency set commit in `rp_begin_ex` (a kernel call), and the same return-value autorelease in `pso_get` / `fs_fn_border` / `vs_fn_for`.
- **CPU-mirrored texture freshness check: one range lookup and 1 MB chunk skipping (`TOTK_REPLAY_FAST`, default on, `=0` goes back to the old path; 2026-10-23, compiled only, not tried in game).** Finding: the dirty tracker was already page-level (a generation per 16 KB page plus a per-pool "latest"), and with `TOTK_TEX_CHECK_ONCE` each texture is already checked at most once per submission, so the cost of the ~152 samples in `tex_mtl` under `tex_by_id` (15 s profile, 1.4.3) was: re-uploads `pkg_upload` ~33 and small-texture hashes `pkg_hash` ~23 (both real work), and ~55 in the tracker itself (`nvn_dirty_tracked` and `nvn_dirty_since` each looking the pool up again, and a page-by-page scan of large textures in pools where something else was written). Now `nvn_dirty_check` does both in one lookup, and each pool keeps the highest generation per 64-page chunk (raised in `unprotect_page` after the page's own generation and before the pool's "latest" and the second "now" step), so the scan skips every chunk not written since the stamp. The answer is the same as `nvn_dirty_tracked` + `nvn_dirty_since` (generations only grow; `make probe-dirty-race` compares both over 16,000 random ranges / stamps and fails with 5,121 differences when the chunk update is removed). Expected: roughly 25–45 of the ~55 samples (about 0.03–0.05 ms per frame); memory: 8 bytes per MB of tracked pool. Not done: caching texture views across slot re-registrations (`newTextureView` ~51 samples): views are rebuilt when a slot is re-registered with another descriptor, after a re-upload (new base texture, so a new view is required anyway) and after a serial is finalised; a cache keyed by (base texture, format, type, levels, slices, swizzle) would keep old base textures alive (the ~11 GB slot-view leak that `treg_drop_serial` fixed), so it needs per-cause counters first and an owner that drops entries with their base. Also not done: `ns_returns_retained` on `tex_mtl` for its autorelease return (~20 samples).
- **The argument-buffer binding loop runs without diagnostic checks when no diagnostic is on (`TOTK_REPLAY_FAST`, default on, `=0` goes back to the old path; 2026-10-23, compiled only, not tried in game).** `encode_args` is about 30 % of `draw_inner`, and its per-binding loop tested a dozen diagnostics on every binding (pass dump, `DM_GFXUSE` recording, `DM_RES_CHECK`, `TOTK_NAN_TRACE`, `DM_NVN_TEXPNG_FS`, the `DM_NVN_FLASHHDR` key compare, `DM_NVN_WATCH_SB`). The loop is now one `always_inline` function (`ea_bind_loop`) instantiated twice with a constant `diag` argument, so the production copy has none of those tests or calls; `ea_diag_any()` picks the copy (pass dump window and environment switches cached per frame; `DM_GFXUSE` recording and the live texture-PNG switch read on each call). The per-fragment-encode `strncmp` against the flash-HDR shader key now runs only when `DM_NVN_FLASHHDR` / `DM_NVN_TEXPNG_FS` is set. Binding results, residency (`USE`) and the `TOTK_TEX_SLOTS` cache / MDIE cross-checks are unchanged; with any diagnostic on (or `=0`) the loop is the old one. Expected: a few percent of `encode_args`; check `encode_args` self time in a Time Profiler A/B. Not done (from the MoltenVK / Ryujinx study): (3) taking `registry_lock` only on a cache miss is not sound as the tables stand: `mtl_reg_tex` / `mtl_reg_samp` `realloc` `g_treg` / `g_sview` / `g_srid` (a lock-free reader can touch freed memory), write multi-word entries with the generation bumped before rather than around the write (no seqlock), and `treg_clear_view_locked` `CFRelease`s views a lock-free reader may be holding; it needs never-freed (chunked) tables, a seqlock generation on every writer and deferred view release first. (1) per-register change counters would mostly duplicate `TOTK_TEX_SLOTS`, which already skips re-resolving unchanged texture / sampler handles; the rest are uniform / storage buffers, whose renaming (`upd_shadow`, `usnap_find`) must be re-resolved anyway. (4) cross-pass argument-buffer reuse: the pass serial in the reuse key is not the only barrier, since `rp_begin` / `pg_compute` call `args_dirty_all()` (bumping `g_args_epoch`) for every new pass; the per-pass state the reuse would have to prove unchanged is `ui_mat_patch`'s ring copy (keyed by `g_pass.serial`), `ser_gate()` texture materialization at pass start, and uniform snapshots (`g_usnap_drops`), so a `TOTK_ARG_CROSS_PASS` switch needs those keyed explicitly before dropping the pass-start invalidation.
- **Fragment shaders that ask for early fragment tests get `[[early_fragment_tests]]` (upstream PR #222 by feeeei, ae8f4f4, with upstream 8e72338 and 92957c9 it builds on; translation chain `totk-native-v8-unverified`; 2026-10-23, compiled and unit-tested only, not tried in game).** Before, `totk_xlate` passed `earlyZForce = false` for every shader, so no MSL declared early fragment tests, and Metal tests depth after any fragment shader that writes memory: about 2,867 cached fragment shaders store to storage buffers (every material shader's per-tile class flag, both lighting shaders), so the ~2,040-draw G-buffer pass, drawn after a depth prepass with an EQUAL test, ran with late depth testing and no early-Z / hidden-surface removal. Now the runtime (`totk_shader_rt.m` variant_request) and `prepare_shader_seed.py` read the fragment shader's NVN control byte +0x718 (0x880-byte sections only; Breath of the Wild's shorter ones are not read) and send `early_fragment_tests`, which `totk_xlate` hands to Ryujinx as `earlyZForce`. 1,677 of 13,645 1.4.3 fragment shaders set it, 775 of them storers without discard; none writes depth. Also a correctness fix: the late depth differed by an ulp from the prepass's, so the EQUAL test failed along contour lines (dotted stone lattice on Great Sky Island). Cost: the chain bump makes every player's shader cache and the seed translate again once on the next launch. Expected: lower G-buffer GPU time from early-Z rejecting hidden fragments; measure with `TOTK_TIMELINE` GPU busy before/after. Risk: the prebuilt `totk_xlate` is upstream's binary, which lacks this fork's patch 0006 (runtime texel offsets; moved to `games/totk/tools/totk_xlate/patches/pending/` until a rebuild with .NET), so the two agl_technique_pfx compute shaders fail to translate again; and its translator log notes are in Chinese until a rebuild from this tree's English `Program.cs`.
- **Why a render pass ends (logging), and sampling draws in a continued pass (`TOTK_PASS_CONTINUE`, default off, `=1` on; 2026-10-22, compiled only, not tried in game).** Conclusion from reading the code: identical SetRenderTargets calls have long been continued by default (`TOTK_RT_CONTINUE`, comparing texture serials and views), so adjacent passes of the same shape such as #36 / #37 / #38 (colour 5, depth 252, all loaded) are not split by "the same targets set again"; the only possible causes are: the target set actually differs (the fifth attachment or a view changed), a copy / buffer update / dispatch / texture clear in between, a clear arriving in the continued pass (but the later pass loads everything, which rules out clearing this set's attachments), or a draw in the continued pass sampling one of the pass's attachments. That last case used to split regardless of which attachment (`draw_samples_rt`), even when the sampled attachment (usually depth, with decal depth test on and depth write off) had not been drawn in this pass at all. Now every pass end records a reason: the pass dump's `W <pass> pass end reason=…` line, and at the end of each `TOTK_PASS_GPU` line `ended-by …` (one more column in the file); the reasons are `set-rt` / `set-rt+clear` / `copy` / `copy-t2t` / `dispatch` / `clear-tex` / `cont-clear` / `cont-samples-att` / `samples-drawn-att` / `cont-samples-drawn-att` / `tex-prepare` / `metalfx` / `other` (end of submission and so on). With the switch on, the continuation point marks every attachment drawn so far as "must be stored before sampling", and sampling draws go to the precise `att_unstored_read`: a draw that samples only attachments that were loaded and not drawn stays in the pass, while one that samples a drawn attachment still stores it first, which matches the visibility of the old split at SetRenderTargets. Log every 600 frames: `[totk] TOTK_PASS_CONTINUE: N render passes ended, M same-target continuations; sampling draws in a continued pass: K stayed in it, J still ended it`. Not done: storing undrawn attachments as DontCare already exists (`DM_NVN_UNWRITTEN_DC`) but only takes effect with `DM_NVN_TBDR=1` (`sd_finish` always stores with TBDR off); Metal says contents are undefined after DontCare and Apple GPUs merely preserve them in practice, so it was not split out on its own. Risk: the sampled attachment is attached to the pass at the same time (loaded only, not written), relying on the Apple GPU reading the original value from memory, which decals in non-continued passes have long done; when the two binding walks (`draw_samples_rt` and `draw_att_reads`) disagree on attachments, it falls back to splitting. If few splits are saved (see `K`), the gain is limited to a few decal passes.
- **Residency-set commits leave the render-pass path (`TOTK_RES_BATCH`, default on, `=0` goes back to the old path; 2026-10-23, compiled only, not tried in game).** Finding: `rp_begin_ex` itself never commits; the ~288 samples / 15 s come from `chunk_maybe_split` → `mtl_sub_split` → `res_commit` before every mid-submission chunk commit (every 40 draws), and the set was almost always dirty there because GPU completion handlers retire textures (`defer_drain` → `res_remove`) while the replay runs. Now the dirty flag is atomic and split into "added" and "removed": `res_commit` returns before any lock, ObjC call or `gpu_budget_check` unless an allocation joined the set (additions are still committed on the committing thread before the command buffer, exactly as before: Metal applies a queue's residency sets as committed when each command buffer is committed), and removal-only changes are committed once per submission on a background serial queue (`res_commit_sub_end`). A removal only ever happens after the submissions that used the allocation completed, so keeping it resident a little longer cannot fault; it only holds that memory wired up to about one submission longer. `gpu_budget_check` now runs only when the set may have grown (`q4_commit` still checks before every command buffer). Log every 600 frames: `residency frames A-B (TOTK_RES_BATCH=1): X commits/frame before command buffers, Y removal-only commits/frame in the background, Z commit points/frame clean or deferring removals (of N checks/frame)`; for A/B compare X with `=0` and the replay thread's `res_commit` samples. Risks: the background commit holds `g_res_mu` during its kernel call, so a `res_add` on the replay thread at that moment waits for it (rare: once per submission); not done: committing additions asynchronously (they gate the command buffer that uses them, so the replay thread would have to wait for the commit anyway).
- **Shader math mode is a choice: `TOTK_MATH_MODE=safe|relaxed|fast` (default safe; 2026-10-23, compiled only).** `TOTK_FAST_MATH=1` stays as the old spelling of `fast`; `relaxed` (`MTLMathModeRelaxed`) allows reassociation and contraction but keeps infinities and NaNs; before macOS 15 / iOS 18 only safe and fast exist and relaxed compiles as safe. Caches: the precompiled shader libraries (the app's `shader-libs` and iOS `shaders.pack` metallibs) are safe-math builds and are skipped in any other mode (compiled from source instead); the pipeline archive goes to `pipelines-relaxed` / `pipelines-fast` next to `pipelines`, so a measurement run never overwrites the safe-math archive files (Metal would only miss on them, but then rewrite them with the other mode's code). Metal's own system shader cache takes the compile options into its key (not verified here), so nothing was done for it. Log once when not safe: `[experiment] TOTK_MATH_MODE=…`. Risk: pictures from relaxed / fast runs are not evidence of correctness (fast breaks the tile-light vertex shader's integer-division idiom); the first run in a new mode compiles every shader and pipeline again.
- **A uniform copy builds on the previous copy of the same range in this replay (`TOTK_SHADOW_INCR`, default on, `=0` rebuilds every copy the full way; LudovicLemarinel 8ecce5b / upstream #257, 2026-10-23, compiled only, not tried in game).** `upd_shadow` used to rebuild each private uniform copy from the submit-time snapshot plus a walk of every pending write; a newer version of a range copied earlier in the same replay is now that copy plus only the writes noted since. It applies only while `g_mat_gen` is unchanged (bumped by a new submission, the snapshot table rebuilt or a range dropped from it, a GPU copy noted, the pending table full) and no GPU write completed meanwhile; otherwise it takes the full path. The source measured 96% of copies taking the incremental path on BotW. The extent half of that commit is already covered by our `TOTK_CB_EXTENT`. Log: the periodic `[nvn] uniform renaming` line now shows `(N incremental)` after the new-copy KB. Risk: a missed invalidation gives a draw stale constants (wrong matrices: objects in the wrong place for a frame), not a crash; `=0` for A/B.
- **Vertex stream GPU addresses are cached per replay thread (`TOTK_VBUF_CACHE`, default on, `=0` off; DavidZande a4b1b7d, from nxnative 697df75, 2026-10-23, compiled only).** `bind_vertex_streams` resolved each bound stream with `mtl_gpu_addr` on every draw; now a thread-local slot per stream keeps the GPU address while the guest address and `g_pool_gen` (bumped under `g_mu` on every pool add / removal) are unchanged. Our per-thread pool cache (`TOTK_POOL_TLS`) already made the lookup cheap, so the gain is a smaller scan per stream per draw. Log: `[vbuf-cache] enabled=… reused=… resolved=…` in the memory line; `probe-gpu-vertex-streams` gained a reuse check and a "pool change forces fresh lookups" check (not run: it boots the game binary headless). Risk: a stale address only if a pool changed without bumping the generation.
- **Large command recordings are handed over without copying (`TOTK_REC_TAKE`, default on, `=0` always copies; DavidZande 5352ab7, 2026-10-23, compiled only).** BeginRecording now reserves the copy prefix in front of the records; at EndRecording a recording of at least 8 KiB that fills at least half its buffer becomes the handle's storage as is, and the command buffer gets a fresh buffer of the same size (the source measured recording-copy time on the game thread −40–50%). Smaller ones are copied as before (`flatten_recording`, now starting after the prefix). The inline-bulk probe gained a "handle unchanged after its command buffer records again" check and a "something was handed over" check. Log: the `[cmd] recording copies` line ends with `handed over without copying N (X MiB)`. Risk: memory per handed-over recording is its buffer's capacity (up to 2x its size) rather than its exact size. The source also turned `TOTK_INLINE_BULK` on by default; that part was not ported (still off here).
- **Textures the CPU rewrites every frame stop faulting (`TOTK_PKG_HOT`, default on with `TOTK_TEX_CHECK_ONCE`, `=0` off; DavidZande 5352ab7, 2026-10-23, compiled only).** A CPU-pool texture re-uploaded 3 frames in a row becomes "hot": its pages are left writable and it is checked by a content hash once per submission (like the small `pkg_hashed` ones) instead of protect → fault on every page → re-upload. After 180 quiet frames (doubling each time it comes back, up to 128x) it is stamped, protected and hashed again, and goes back to page tracking if unchanged. The source saw ~800 write-protect faults a frame and 35–90 ms frames in play. The source's write-barrier guard (`TOTK_FENCE_LAG`) does not exist here and was left out, as was its writer-ring logging. Log: `[hot] … checked by content now` / `… page protection again`, plus `[pkg-hot] enabled=… in=… out=… checks=… hash_ms=…` in the memory line. `make probe-dirty-race` passes (17 checks). Risk: the hash costs a full read of the texture each submission while it is hot, and a write that exactly preserves the hash (practically impossible) would be missed.
- **Environment switches are read once (Yong Li c0c6b26, 2026-10-23).** That commit's two changes were already here: `TOTK_DIAG_ENV_ONCE` is on by default (so `bindprog_env` runs `getenv` once, with `=0` bringing back the per-call lookup for A/B), and EndRecording's `TOTK_CHAIN_LOG` was already cached in `chainlog_env`. What was left: the per-submit `TOTK_CHAIN_LOG` lookup in `nvnQueueSubmitCommands` now uses `chainlog_env`, and the per-present `TOTK_MFX_DUMP` lookup is read once. The remaining per-call `getenv`s on hot paths are in `encode_args` (only after a specific shader key matches, so rare) and were left alone because other work is editing that function.
- **Selective fast math as a text pass over translated MSL (`TOTK_MSL_FAST`, default 0, `=1` on; parts `TOTK_MSL_FAST_DIV=0` / `TOTK_MSL_FAST_FUNCS=0` turn one off; 2026-10-23, compiled only, not tried in game).** The math mode stays safe; `totk_msl_fast.h` rewrites fragment shaders only, in `totk_msl_library` (the one place translated MSL becomes a library: warm-up, first use, patched variants, the shell's source-in-place libraries): `float NAME = A / B;` with single-token operands becomes `fast::divide(A, B)`, and `log2` / `exp2` / `sqrt` / `rsqrt` in `floatN NAME = ...;` lines get `fast::`. A value that reaches `as_type<int|uint…>(…)` or an `int(…)` / `uint(…)` conversion stays precise: those identifiers are sinks, closed backwards over `NAME = EXPR;` statements, so Maxwell's integer-division idiom (`float _a = 1.0 / _b; int _c = as_type<int>(_a) + (-2);`, the likely reason `TOTK_FAST_MATH=1` broke rendering) is never touched. Over every 20th cached shader (1,249 files of `rt-totk-native-v6-unverified`): 2,136 divides rewritten, 2,056 kept precise (most feed integer texel coordinates, which is the conservative side), 4,214 calls; about 1 ms per shader. 20 rewritten real shaders (10 with the idiom) compile with `xcrun metal -fmetal-math-mode=safe -c`; a rewritten shader that does not compile falls back to the original (logged, at most 5 times). Self-test: `make probe-msl-fast` (snippets, under a second; with `<out dir> <files…>` it rewrites real shaders). Not done: the NaN guards on sample coordinates (`select(c, float2(0.0), isnan(c))`, 179k in the cache). They come from the Ryujinx SPIR-V backend in `vendor/ryujinx` (`CodeGen/Spirv/Instructions.cs` around line 1243), present since the first import (dd0e893) with no commit message, document or patch file (`games/totk/tools/totk_xlate/patches` has no such patch, and `vendor/ryujinx/README.md` calls the copy unmodified). It applies to every float-coordinate sample, presumably to match Maxwell's NaN-as-zero texture coordinates where Metal's result is undefined; with no narrower reason on record it is left in. Risks: approximate divides and transcendentals in fragment shaders can shift colours or bands slightly (Switch hardware is approximate too, but not the same approximation); the first run with the switch compiles every shader and pipeline again.
- **Decal splits read from the tile instead (`TOTK_ATT_FB=1` or `TOTK_FB_FETCH=1`, default off; `TOTK_ATT_FB_WRITTEN=1` also reads slots the draw writes; 2026-10-23, compiled and GPU-probed only, not tried in game).** Background: a Ryujinx Metal fork measuring TOTK 1.4.2 on an M1 Max (sunsssyc/Ryujinx_Optime d5835430 / e186fff2 / 02f6962c) found nearly every `samples-drawn-att` split is a draw sampling the full-size R32Float linear-depth colour attachment at its own pixel, and turning that sample into a `[[color(n)]]` read cut render passes per frame 278 → 186 and GPU busy 81 → 65 %; their hard rule: never tile-read a slot the same draw writes. Port: upstream PR #155 (feeeei, `nvn_fbread.h`) rewrites the fragment MSL so each sample of a chosen attachment returns the tile value when `floor(uv * size)` is the fragment's own pixel and samples memory otherwise; the test is per fragment at run time, so no proof of the vertex shader's projective UV pattern is needed, and a texel-offset sample always reads memory (added here; PR #155 forwarded the offset but compared only `uv`). Added on top of PR #155: the written-slot gate (declared output and write mask, Ryujinx's rule) on by default; the encoder slot check (the texture must be colour attachment j of the open encoder, level 0 layer 0), which lets it work in a continued pass; and a continued pass stays open (no `cont-samples-att`) when every attachment the draw binds anywhere is read from the tile. Diagnostics (with `TOTK_PASS_GPU` or the pass dump on): the reason becomes `samples-drawn-att[c<index>:<format>:w<write mask hex>:o<declares output>;…]fb=<why the tile read did not take it>` (`off`, `written`, `border`, `depth-att`, `view`, `enc-slot`, `pass-kind`, `msl`, `not-texture`, `other-stage`, `depth-out`; `partial` = some taken), and every 600 frames `[totk] [fb-fetch] through frame F: N draws read their own attachments from the tile (K of them kept a continued pass open), R sampling draws refused`; the first 32 variants log `[totk] [fb-fetch] shader <key>: reads n of its own attachments from the tile (…)`. To try: Sky Temple save, `TOTK_PASS_GPU` on, compare `samples-drawn-att` counts and GPU ms with `TOTK_ATT_FB=1` against off, then with `TOTK_ATT_FB_WRITTEN=1` (look at overlapping decals). Risks: linear filtering at a not-quite-centred uv returns the exact texel instead of a blend (tiny difference, Ryujinx accepted it); the first use of each shader compiles its variant on the submit thread (about 90 ms, a hitch); a draw that may be skipped is deferred while its pipeline compiles (a decal missing for a few frames). Remaining plan: if the `fb=` tags show most splits are refused for `written`, look at which slot is written and whether a per-slot partial take (fetch the unwritten ones, keep storing for the written one) would ever avoid the split (it cannot while the written slot is also sampled); if refused for `border`, combine the border and tile-read rewrites into one variant.
- **Pipeline MRU per program (`TOTK_PSO_MRU`, default on, `=0` off; 2026-10-23, compiled only, not tried in game).** Like Ryujinx `Program.TryGetGraphicsPipeline` / MoltenVK `changePipeline`: each `NvProg` keeps its last four final pipelines, keyed by `g_pso_state_gen` (bumped by `PSO_DIRTY()` wherever `g_pso_dirty = 1` was set for a state change and wherever `S` is replaced wholesale), the pass signature (colour / depth / stencil formats, samples, layered, MetalFX role), the vertex / fragment shader objects and the border keys of both stages compared by text. A hit skips `pso_key_fill`, `fs_fn_border`, `vs_fn_for` and the pipeline hash lookup on pass changes, program changes (a program bind no longer bumps the generation, the program owns its MRU) and on every draw of a shader that met an emulated border colour. Plain stand-ins while a border variant compiles, deferred draws and merged passes are never remembered. Log every 600 frames: `[totk] TOTK_PSO_MRU: N pipeline lookups answered by the program's MRU, M went to pso_get`. Risk: a state input of `pso_get` changed without `PSO_DIRTY()` would draw with the previous pipeline (wrong blend / mask / vertex layout); every writer of those `S` fields found by grep bumps the generation.
- **NVN discards are honoured (`TOTK_DISCARD`, default 1, `=0` ignores them as before, `=2` also turns the next pass's load DontCare; 2026-10-23, compiled only, not tried in game).** `nvnCommandBufferDiscardColor` / `nvnCommandBufferDiscardDepthStencil` had no handler, so the calls were dropped and the attachments stored anyway. They are now recorded (`OP_DISCARD_COLOR` / `OP_DISCARD_DS`); in an open pass the matching attachment is marked and `sd_finish` stores it DontCare if no draw (clear quads included) was encoded after the discard; with no pass open nothing changes unless `=2`, which makes the next pass's Load of that same subresource DontCare (the repo's NVN headers have only the prototypes, so "discard = contents undefined" is taken from Vulkan / Metal semantics, not proven from NVN documentation). Skipped during layered / merged passes, deferred replays, hoisted clears and disabled conditional rendering. Log: `[nvn] discards and empty passes to frame …` (game calls per frame, attachments marked, stores and loads made DontCare). Risk: if the Switch driver treats a discard as a no-op and the game reads the target afterwards, that read sees garbage on Apple GPUs.
- **Empty passes store nothing (`TOTK_EMPTY_PASS_DC`, default on, `=0` off; 2026-10-23, compiled only, not tried in game).** Like Ryujinx `FixupStoreActions`: a render pass that encoded no draw at all (every draw skipped, for example while its pipeline compiles in the background) stores its uncleared attachments DontCare instead of writing them back unchanged; cleared attachments and passes with block-render write-backs still store. Counted in the same `[nvn] discards and empty passes` line. Risk: Metal calls a DontCare-stored attachment undefined; this relies on Apple GPUs keeping a loaded, untouched attachment (what the UDC self-test `DM_NVN_UDC_SELFTEST` measured on A19), which this document earlier declined to rely on for `DM_NVN_UNWRITTEN_DC`.
- **Mid-submission commits also by replay time (`TOTK_CHUNK_US`, default 300, `0` = draw count only; 2026-10-23, compiled only, not tried in game).** Like Ryujinx `AutoFlushCounter` (1.5 ms there): at the existing split points (where a new encoder is about to open; a render pass is never split) a commit now also happens once 300 us of replay have passed since the submission began or the last commit and at least 10 draws were replayed, besides the existing 30 / 40 draw counts. The `[nvn] chunked submits` line now shows how many chunks per frame the timer caused. Risk: more commits per frame (each `rs_sync` + residency commit); tune or set `0` if the extra commits cost more than the earlier GPU start saves.

## The critical path and today's measurements (2026-10-22, M3 Pro, 1800p scene / 4K output, Sky Temple save copy)

- **The game keeps only one frame in flight.** `TOTK_SYNC_LOG=1`: the main thread waits on a fence once per frame (about 10.8 ms), always for the frame the render thread just submitted; the GPU finishes → about 0.85 ms later the render thread submits the next frame. `TOTK_TIMELINE` over 20 frames: submit → GPU start 0.8 ms, GPU busy about 15 ms, GPU idle within the frame about 2.2 ms.
- **Where the idle time comes from:** the main G-buffer pass of about 2040 draws (3200x1800, 4 colour + depth) takes 2.5 ms to replay and cannot be submitted before the pass ends, so the GPU has nothing to do meanwhile. So replay thread A's CPU time before this pass (about 4.3 ms) counts almost one for one in the frame time; encoder thread B never holds things up (A waits for B < 0.1 ms per frame). Splitting this pass would mean storing / loading five 3200x1800 targets one more time (about 120 MB each), which saves nothing.
- **Faster replay (`TOTK_REPLAY_FAST`, default 1) plus upstream #286 / #287:** submit CPU per frame 6.74 → 6.24 (the two upstream items) → 5.75 ms; frame time p50 18.05–18.22 → 17.87–18.04 ms, p95 about 0.4 ms lower.
- **Tried and left off:** `DM_NVN_TBDR=1` as a whole (frame 18.5 → 25.5 ms, GPU 15.1 → 16.3 ms, plus 8 red "pass without Metal targets" lines); `TOTK_PASS_CONTINUE=1` (all 6103 sampling draws read attachments just drawn in the same pass, 0 could stay in it, frame time unchanged). The decal passes after the G-buffer (#36 → #37 → #38) have a real dependency between them (`samples-drawn-att`).
- **This round of upstream work (the rest of tvc97 3a5d46f, #286 / #287, write-back / ReadTexels, the nine shader / pipeline stutter fixes)** shows no measurable change in steady-state frame time; they target stutter, loading and write-back, not the per-frame critical path.
- **The `DM_NVN_TBDR` pieces, measured one at a time (2026-10-22, same setup):** baseline frame 17.84 / GPU 14.86 ms. `GUARDS` alone (no mid-submission commits, no async shaders, no layered passes) gives frame 22.98 / GPU 16.10 ms, so it is the whole cost of the old bundle. Read against `GUARDS`: `STORE` makes 6 stores a frame DontCare and changes nothing measurable (16.08); `LOAD`, `FUSE` and `ZSKIP` never fire in TOTK's world (0 hits). The 0.44 ms per frame lookahead index (`IDX`) is pure cost. Nothing in the bundle is worth separating from `GUARDS`; all pieces stay off.
- **Two frames in flight (`TOTK_FRAMES_IN_FLIGHT=2`, experimental, default off; 2026-10-22).** A main-thread wait on the newest fence of a fence-sync object waits for the fence that object held one frame earlier, so the GPU can run up to one frame behind the game. M3 Pro, 1800p render / 4K output, auto cap 60, keepalive off: frame p50 18.07 → 16.88 ms (at the cap), but p95 19.2 → 26.0 ms and frames over the beat 16 % → 30 %; GPU busy 79 % → 97 %, yet GPU time per frame 15.0 → 16.4 ms (CPU and GPU now share power / bandwidth) and the replay 6.8 → 9.2 ms wall. A still screenshot shows no corruption. Unverified: whether the game rewrites memory the GPU still reads for the previous frame (would show in motion: skinned characters, particles, cloth); uniforms are safe (snapshotted at submit), zero-copy vertex / storage buffers are not proven. Log: `[nvn] frames in flight: N fence waits moved one frame back`.
- **Frames in flight made guarded (2026-10-23; still `TOTK_FRAMES_IN_FLIGHT=2` only, default off; untested in game).** Inventory: the GPU reads guest memory zero-copy for vertex / index / storage / indirect buffers, buffer textures and GPU texture decode (pools wrapped with `newBufferWithBytesNoCopy`); uniforms (`usnap` / `upd_shadow`) and CPU-mirrored textures (re-uploaded into a fresh `MTLTexture`, old one recycled only after its fence) are copies. Now: every pool a submission looks up gets that submission's fence and its pages are made read-only at commit (`nvn_dirty_guard`, only 1 MB chunks written since the last pass are re-protected); a CPU or host write to such a page waits in the fault handler until the fence completes. Pool invalidates wait for the newest in-flight GPU write of the range (storage writes, texture→buffer / buffer copies, uniform updates, counters); learned readback compute shaders end a command buffer right after their dispatch so the wait is for that early commit only (port of DavidZande's `TOTK_LAG_READBACK=2`, 6a87c04 / bdb8946). Completion-time event / counter writes are skipped where the game rewrote the destination since replay (`TOTK_FIF_POST_CHECK=0` off). Pool finalize waits for the pool's last reader. A lag over submissions with counter reports (`TOTK_FIF_COUNTERS=1` lags anyway) or an unguardable pool falls back to the real fence. `TOTK_FIF_AUDIT=1` waits for nothing and only counts would-be waits with sample pages (does TOTK multi-buffer its dynamic data?). Log every 5 s: `[fif] last N s: … waits lagged one frame, … fell back …; guard: … fault waits (… a frame, … ms a frame) …; readbacks of in-flight GPU writes …`.
  - Remaining: (1) the guard is per pool, not per page: a write anywhere in a pool waits for the pool's newest reader, so large shared pools may wait more than needed — per-range recording needs real binding sizes (many lookups pass length 1). (2) Counter reports: TOTK uses occlusion queries every frame in the world, so with the default fallback the lag may rarely engage; measure with `TOTK_FIF_COUNTERS=1` (results one frame late) and check for popping. (3) GPU→CPU reads without a pool invalidate (uncached pools, `nvnBufferInvalidateMappedRange` is a no-op) are not covered. (4) Port DavidZande's storage snapshot (41de26e: read-only storage bindings ≤ 64 KiB captured at submit, the glyph-instance flicker) to turn the guard's fault waits on those into copies. (5) Storage-shared textures (`TOTK_TEX_SHARE`) reuse pool memory through cached texture objects that may not go through the pool lookup in a given submission; confirm they are covered or flag them. (6) Translation-thread mode (`TOTK_ASYNC_REPLAY=1`) is not lagged at all. (7) Fault-handler waits poll with `nanosleep`; measure the cost of the per-frame faults the guard adds (`fault waits` and the `mprotect` line).
- **Frames in flight: untracked pools and counter reports no longer block the lag (2026-10-23; still `TOTK_FRAMES_IN_FLIGHT=2` only, default off; not run in game yet).** A 120 s `TOTK_FIF_AUDIT=1` run (M3 Pro, Sky Temple) showed ≈1 CPU write a frame to pages in flight, but no wait ever lagged: about 20 pools a frame were "untracked" and about 3 counter reports a frame forced the real fence. (The old line's fallback counts were cumulative since start, not per 5 s; the new lines are per window.) Pool classes and decisions:
  - **Pools sharing a host page with a neighbour** (the untracked ones). NVN pools are 4 KiB aligned, host pages 16 KiB; `nvn_dirty_add_range` refused any pool overlapping a tracked range, so the second of two adjacent pools went untracked as a whole (also: all its textures counted as dirty on every use). Now the new range is clipped to the pages no range covers (the shared page stays with the older range), the guard and the finalize wait walk every range a pool spans, and `nvn_dirty_remove_range(mem, size)` removes the range that pool registered (before, finalizing a pool inside or next to another removed the neighbour's range by `find(mem)`). Still untracked: a pool whose span strictly contains an older range (counted, not expected), and a pool's shared edge page after the neighbour that owned it is finalized (guard returns 0 → real fence, safe).
  - **Virtual pools**: the GPU reads them at their own address, but the CPU writes the physical pool's storage at another address with its own protections, so guarding the virtual range alone was not enough. `totk_vpool_guard` now also guards the physical storage mapped into the read range (mapping table entries a newer mapping overlaps are dropped; a full table makes virtual pools unguardable → real fence).
  - **CPU_NO_ACCESS / CPU_UNCACHED / COMPRESSIBLE pools**: registered and guarded like any other (our own host writes into them go through `prep_write`, which waits too); nothing to change. **GPU_NO_ACCESS pools** are never registered for the GPU, so no submission reads them.
  - **Counter reports**: every type except SAMPLES_PASSED is written by the completion handler as `{0, completion time}` (no real statistic exists), so a lag over timestamp / statistics reports is now allowed by default (results one frame late, as on hardware with its own queue depth; a pool invalidate over a record still in flight waits for it). SAMPLES_PASSED (occlusion culling) keeps the real fence. `TOTK_FIF_COUNTERS=1` lags all, `=0` lags none. The first report of each type is logged once (`[fif] first counter report of type …`).
  - Log every 5 s, per window: `[fif] last N s: … waits lagged one frame (… over timestamp/statistics reports), … fell back to the real fence: occlusion reports …, timestamp/statistics reports …, untracked pool pages …, virtual pool backing …, pool set overflow …, not recorded …`, then `[fif]   submissions …` (per-class submission counts, unguardable pools, virtual pools, pool registrations clipped / covered / untracked), `[fif]   counter reports by type: …; pool invalidates over a counter record … (… in flight)` (whether the game invalidates before reading counter results) and `[fif]   guard: …`. Probe: `make -C games/totk probe-dirty-race` (shared-page cases added). Next: one audit run; if occlusion reports remain the main fallback, measure `TOTK_FIF_COUNTERS=1` for popping.

## Frame interpolation: MetalFX parameters and per-object motion vectors (2026-10-23, compiled only, not tried in game)

- **Interpolator parameters (`totk_mfx.m`, on whenever `TOTK_MFX` is).** WWDC25 session 211 lists deltaTime, near / far plane, field of view, aspect ratio, depthReversed and jitter as the parameters that cause occlusion artefacts when wrong. They are set every frame: near / far, vertical field of view (degrees) and aspect ratio now come from the projection rebuilt as view-projection (camera block floats 12..27) times the inverse view (floats 0..11); an infinite far plane is given as 1e7; when the product is not a perspective projection the block floats 56 / 57 / 70 / 62 are used as before. `TOTK_MFX_PROJ=block` forces the old values (A/B). deltaTime (measured interval between the two game frames), depthReversed = NO (D32F, GL-style clip depth mapped to 0..1, which has the same depth curve as Metal's 0..1 projection with the same planes) and zero jitter (FXAA; with `TOTK_TAA` the colour given is the TAA output) were already right. The first frames log `MetalFX projection from the matrices: near … far … fov … aspect … (block floats: …)`: check once in game that both agree in near / fov / aspect; a mismatch means the view layout guess (floats 0..11 as 3x4 rows) is wrong and the fallback should stay.
- **Per-object motion (`TOTK_OBJ_MOTION=1`, default 0, needs `TOTK_MFX`; `totk_objmv.h`).** Approach of RTX Remix (`rtx_draw_call_tracker`, `rtx_instance_manager`). Passes into the G-buffer depth that MetalFX takes (D32F of the colour size, three or more colour targets, at most six, not layered, not a readable-tile merge) get an RG16Float motion target at colour attachment 6 (cleared to OBJMV_NONE = 65000 by the first such pass of the frame). Opaque triangle draws there (depth test on, no blending, no alpha-to-coverage) get role `MFX_ROLE_MOTION`: a vertex variant stores `gl_Position` to `cur[(instance - base instance) * nv + (vertex id - base vertex)]` in this frame's position arena (three private arenas of `TOTK_OBJ_MOTION_MB`, default 64 MiB, in turn) and reads `prev[]` of the previous frame for the same draw (constants at vertex buffer 13); a fragment variant writes `prev.xy / prev.w - cur.xy / cur.w` to colour 6, OBJMV_NONE when unknown or more than one NDC unit (half the screen) away. Draw identity: vertex shader, vertex buffer of attribute 0, index buffer, first / base vertex, count, instances, vertex range, primitive, and the ordinal among this frame's draws with those. Every other draw of such a pass has write mask none on attachment 6 (`PSO_OBJMV`, a2c bit 5). The motion kernel uses the object motion where it is below 16 NDC units and the camera reprojection elsewhere. Motion pipelines are not recorded in the warm lists. Log every 600 frames: `[mfx] TOTK_OBJ_MOTION: … motion draws, … matched the previous frame, … new, … without a vertex range, … over the arena`; the 300-frame MetalFX line now says `interpolated frames N (with per-object motion M)`. Variants that cannot be built log `TOTK_OBJ_MOTION: vs … / fs …: no motion variant (reason)` (up to 32 lines).
- **Turn on:** `TOTK_MFX=interp TOTK_OBJ_MOTION=1` (with `TOTK_BACKGROUND=1 TOTK_AUDIO_OFF=1` for test runs). Look at Link running sideways, an NPC walking past, cloth and grass in wind, with the interpolated frame (`TOTK_MFX_DUMP=<dir>` dumps motion textures).
- **Remaining steps / checks, in order:**
  1. First run: confirm the motion pass is found (the log line `per-object motion target WxH` with the 3200x1800-class depth size) and that `matched` is most of `motion draws` while standing still. If `matched` stays near 0, the identity key is unstable (for example vertex buffers renamed per frame): log the key parts of the first 20 draws of two frames and drop the unstable one.
  2. If the picture of the G-buffer pass changes at all (it should not: the motion variants only add an output), compare with `TOTK_OBJ_MOTION=0`; a broken shader rewrite shows up as a `no motion variant` line, a pipeline build failure (`Render pipeline build failed`) or a missing draw.
  3. Validate the sign with `TOTK_MFX_DUMP`: on a static scene with a turning camera, the object motion of the terrain must equal the camera motion (both point to the previous position, pixels of the motion texture). If they are opposite, flip the factor `float2(0.5, -0.5)` in the `mfx_mv` kernel.
  4. Draws excluded today fall back to camera motion (or keep the motion of what they cover, see risks): blended draws, draws needing a fragment border-colour variant, a vertex border variant or a tile read (`g_pso_fbfn`), merged / layered passes. A role-0 opaque draw should write OBJMV_NONE through a small fragment variant instead of leaving the attachment alone.
  5. Pairs with the same identity drawn in a different order between frames (two copies of one model at different places) swap their motion; a per-object constant buffer address in the key would fix that if the game keeps those buffers stable (check in step 1).
  6. Dynamic resolution: like the camera path, the conversion to pixels assumes the viewport is the whole depth texture; if the game renders a sub-rectangle, both need the viewport size.
  7. Cost: one extra RG16Float target (about 23 MB at 3200x1800), 16 bytes per vertex per frame written, a 256-byte constant allocation per motion draw. Measure the G-buffer pass GPU time with and without.
- **Flicker with per-object motion fixed by invariant positions (2026-10-23, compiled only, not tried in game).** With `TOTK_MFX=interp TOTK_OBJ_MOTION=1` textures and meshes flickered; `TOTK_MFX=interp` alone was clean. Most likely cause: the G-buffer pass draws after a depth prepass with an EQUAL depth test (see docs/how-it-works.md, Early fragment tests), and the motion vertex variant is a third vertex function: compiled at runtime from rewritten MSL (position stored to memory and passed on as two more varyings) while the prepass's function usually comes precompiled from the app's shader-libs. All 1,486 cached vertex shaders declare `[[position, invariant]]` and use `fma()`, but nothing compiled them with `preserveInvariance`, so nothing made the variant's position bit-identical to the prepass's; where it differed by an ulp the EQUAL test failed and the G-buffer kept old values. Checked and not the cause: attachment 6 has write mask none and no blending on every non-motion pipeline of the pass (`PSO_OBJMV`, builtin clear pipelines too); the motion role and `PSO_OBJMV` are in the pipeline key and the MRU signature; the other attachments' load / store are unchanged; varyings stay under the limit (at most 96 user components + 8 added); buffer 13 is used by no translated shader. Fix: with `TOTK_OBJ_MOTION=1` every translated shader (originals and all variants) is compiled with `preserveInvariance` (Metal guarantees equal positions only between functions compiled with it), the precompiled shader libraries are skipped and pipelines go to `pipelines-invariant` (`totk_preserve_invariance`; `TOTK_PRESERVE_INVARIANCE=0` / `1` overrides, for A/B). Cost: the first launch with it compiles the shaders at runtime (long warm-up once, Metal caches them after), vertex functions may be slightly slower. Diagnostic `TOTK_OBJ_MOTION_DIAG=1`: motion variants drawn as usual but the motion written as none (camera motion everywhere, like `TOTK_MFX=interp` alone); `=2` writes zero motion. **Check in game:** (1) `TOTK_MFX=interp TOTK_OBJ_MOTION=1`: log `Vertex positions compiled invariant`, no flicker; (2) if it still flickers, add `TOTK_OBJ_MOTION_DIAG=1`: flicker gone means the motion values are wrong (sign, stale motion under non-motion opaque draws, or the next frame's G-buffer pass clearing the motion target while this frame's interpolation still reads it), flicker remaining means the G-buffer draws still differ (then compare `TOTK_PRESERVE_INVARIANCE=0` to confirm the invariance change had an effect, and look at one flickering surface with `TOTK_GPU_HILITE1`); (3) compare G-buffer GPU time with and without invariance.
- **Risks:** wrong pictures in the G-buffer pass if a rewrite is wrong (motion variants are separate pipelines; off by default); motion of a hidden surface left under a non-motion opaque draw (smearing there, not worse than camera motion in most cases); first use of each motion variant compiles synchronously for draws that cannot be deferred (a hitch the first time a shader is seen). The motion target, like the G-buffer depth, is written by the next frame's G-buffer pass while the interpolation of this frame may still read it; this relies on the same queue ordering the depth already does.
- **Debug view of the interpolation inputs (`TOTK_MFX_DEBUG_VIEW=motion|depth|split`, setting *Interpolation debug view*, 2026-10-23).** For judging flicker / ghosting: draws the motion texture MetalFX reads (hue = direction to the previous position, brightness = length, full at 32 px; per-object motion pixels tinted and outlined in white, derived from the motion and per-object textures, so `mfx_mv` is unchanged), the linearised G-buffer depth, or picture / motion / depth in thirds, over both the interpolated output and the game's own frame (`mfx_debug_encode` in `totk_mfx.m`: one render pass per target in the interpolation command buffer after MetalFX; nothing while off). Checked with a scratch probe on synthetic inputs (colours, depth ramp, crop, object outline); not yet looked at in game. Look first at Link while turning: with `TOTK_OBJ_MOTION=1` he should be outlined and keep near-zero motion while the background shows camera motion.

## Frame interpolation memory: resolution changes, the GPU budget and per-object motion arenas (2026-10-23, compiled only, not tried in game)

- **Problem:** with `TOTK_MFX=interp TOTK_OBJ_MOTION=1`, changing the output resolution in game stopped it at `GPU allocated 7387 MB exceeds the budget of 7372 MB` (M3 Pro 18 GB, 1800p render, 3456x1944 output), and a boot test had per-object motion over its arenas for 87% of the draws (`2525842 motion draws … 2194636 over the arena (4194304 of 4194304 positions last frame)`). Fixes (`totk_mfx.m`, `totk_objmv.h`, `nvn_mtl.m`):
  - **Size change:** the old scene / UI / output / motion textures, the old interpolator and the per-object motion target of the old size are retired and released 8 presents later (the game's last frames and the interpolation payloads may still use them; Metal 4 encoders retain nothing). Cached interpolators of another output size or format are evicted (the cache had kept up to four of them, each holding history textures of its output size). Log: `size change AxB -> CxD: N MB of textures of the old size and M cached interpolators … retired`, then `released N MB of retired MetalFX resources (…)` (interpolators' own memory is not reported by Metal, so it is not in that number).
  - **Off / paused:** turning interpolation off releases all of its textures (the interpolator cache stays for a key-2 toggle, see `MFX_FI_CACHE`) and the per-object motion arenas (`[mfx] TOTK_OBJ_MOTION: position arenas released (N MB)`).
  - **Budget:** at every present, above 95% of the GPU memory budget interpolation and per-object motion are paused (`[mfx] near the GPU memory budget: interpolation paused (…)`); the pause also evicts the interpolator cache. It resumes when the use plus what the pause freed (measured after the release) is under 85% (`back under 85% … interpolation resumed`); after three pauses it stays off for the session (key 2 turns it on again; any user change ends a pause). `gpu_budget_check` tolerates an overrun of at most 5% while the pause releases memory (`… over the budget … while frame interpolation is released; going on`) instead of the immediate FATAL; beyond that, or with interpolation already off, it stops as before.
  - **Per-object motion storage:** indexed draws store only the vertex range their indices use (min / max index, scanned once per index buffer / count / type and again every 600 frames), not the whole bound vertex buffer (often a large shared pool range). Draws of more than `TOTK_OBJ_MOTION_DRAW_MAX` positions (vertices x instances, default 65536: terrain, big static meshes, dense instanced foliage) store nothing and keep the camera motion, which is exact for whatever does not move independently of the camera. Arenas start at 3 x 16 MiB and double at the end of a frame that did not fit, up to `TOTK_OBJ_MOTION_MB` (default 64); a growth loses one frame of object motion. The 600-frame line now also gives `over N positions (camera motion)`, the arena size and the index ranges scanned.
  - **Check in game:** change the output resolution with interpolation on and look for the size-change and release lines, with `GPU allocated` in the menu meter settling back; in the world, `over the arena` should be near 0 and `matched` most of the stored draws. If foliage or large animated meshes lose motion, raise `TOTK_OBJ_MOTION_DRAW_MAX`. Not done: classifying draws as static from their stored motion (a draw whose motion equals the camera reprojection for N frames stops storing, rechecked every K frames) needs the reprojection in the vertex variant and a GPU-written flag per draw read back by the CPU; it is the next step if the vertex cap leaves too much out.
